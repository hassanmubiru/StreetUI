# StreetUI 2.5.0 — Dogfooding Report

**Mission.** Build the official StreetUI website entirely with StreetUI, as a real
production application rather than a demo, and treat the act of building it as the test:
if the framework has a weakness, the website exposes it and the finding is classified and
routed to the underlying framework problem.

**Where things stand (2.5.0 final):**

- Source **typechecks**: `tsc --noEmit` → exit 0.
- **Tests pass**: `vitest run` → 13/13, all through the public `streetui` /
  `streetui/testing` API — no private graph access, no second renderer.
- **Bundles build**: all three entries (`index`, `browser-entry`, `server-entry`) compile
  to ESM; the bundled `server-entry.js` runs and renders real SSR HTML.
- **Findings recorded**: 6 classified findings (see `V2.5.0-FRAMEWORK-FINDINGS.md`), zero
  of which were "fixed" by auto-adding an API.
- **Browser benchmarks**: Chrome 153 mount 205.5 ms · hydrate 157.2 ms · 0 mutations fine-grained.
  Firefox 155 mount 307 ms · hydrate 219 ms. No regression vs 2.3 baseline.
- **Visual a11y**: axe-core 0 violations (Chrome 154). PASS.
- **AT-SPI**: tree captured (Chrome present, 16 apps). Literal Orca speech pending (2.6).
- **Published**: `streetui@2.5.0` — 18/18 ✅ on 2026-10-01.

## 1. What the website is

A complete documentation + marketing site: Home, Getting Started, Docs (18 sections across
6 groups rendered by one `/docs/:section` route), API Reference (6 groups), Examples (8,
with a `?q=` filter), an interactive Playground **built in StreetUI**, Benchmarks
(methodology only), Changelog, Blog (2 posts, dynamic `:slug`), About, and a 404 fallback —
13 routes total, served under one persistent shell with a skip link, nav landmark, docs
search, and an SSR/hydration-safe theme toggle.

Architecture detail is in `V2.5.0-WEBSITE-ARCHITECTURE.md`. The one-line summary: the
browser receives nothing hand-written except an empty `<div id="app">`; everything else is
produced by `DSL → compile → graph → runtime → DOM`, the same pipeline the framework ships,
imported the way an external `npm install streetui` consumer would.

## 2. Framework features actually exercised

| Capability | Where in the site |
|---|---|
| `signal` / `derived` / `effect` | theme controller, search results, examples filter, playground |
| Routing (static + dynamic + query) | 13 routes; `/docs/:section`, `/blog/:slug`, `/examples?q=` |
| `router.isActive` reactive active-state | nav links mount an `(active)` marker via `when` |
| Persistent shell + router outlet | shell rendered once; only the outlet subtree swaps |
| `when` conditional subtrees | search empty-state, examples empty-state, active markers |
| keyed `listOf` | search results, examples list, playground list demo |
| Forms / bound inputs | search box, greeter input, playground |
| SSR (`renderToString`) + state serialization | `server-entry.ts` → real 2.5 kB HTML + state script |
| Hydration adoption | server markup re-mounted with `hydrate: true`; node identity preserved |
| `head` metadata | per-route document metadata |
| Testing utilities | `render`-free router mount, `findByRole`, `trigger`, `flushUpdates` |

None of these required a new runtime primitive, a virtual DOM, a second reactive system,
or splitting the public package.

## 3. Findings (summary — full detail in `V2.5.0-FRAMEWORK-FINDINGS.md`)

| ID | Classification | One-line |
|----|----------------|----------|
| F-1 | MISSING PRIMITIVE | No first-class `code`/`pre` node; docs code blocks are container+escaped-text + CSS. |
| F-2 | DX / DOCUMENTATION | `derived` is `ReadonlySignal`; easy to over-annotate as `Signal` (compiler was right). |
| F-3 | API DESIGN | Optional DSL option fields reject explicit `undefined` under `exactOptionalPropertyTypes`. |
| F-4 | API DESIGN / DOCUMENTATION | Custom outlet id + SSR hydration adoption needs key+id agreement in three places. |
| F-5 | DOCUMENTATION | `RouteContext.query` is a `URLSearchParams` (`.get('q')`), not a record. |
| F-6 | TOOLING (sandbox) | `tsup` can't bundle under the mount (`EPERM` on temp-config unlink); esbuild path works. |

Discipline applied: F-1 is a genuinely missing leaf node and is *proposed*, with
justification, **not** silently shipped in this phase. F-2/F-5 are correct behavior
recorded as docs/ergonomics. F-3/F-4 are real public-surface items proposed as type-only /
documentation changes. F-6 is an environment limit, recorded honestly rather than
papered over with a false "build passed."
