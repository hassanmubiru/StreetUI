# StreetUI 1.8.0 — Component & Composition Platform Report

**Release version:** `1.8.0` (minor — additive public API; the v1.0 frozen
surface is untouched).
**Milestone:** Component & Composition Platform (the milestone following the
v1.9 Overlay / Focus platform; the release version is the next coordinated minor
after `1.7.0`).
**Date:** 2026-09-28.
**Publication status:** **NOT published.** The npm registry is unreachable from
this environment — `npm info streetui version` returns `403 Forbidden` — so no
publication was performed and none is claimed.

---

## 1. Objective

Add a first-class, StreetUI-native `component()` abstraction that compiles into
the **existing** pipeline (DSL → Compiler → Semantic Application Graph → Runtime
→ Direct DOM Renderer). Hard constraints, all honoured:

- No virtual DOM, no second reactive system, no second renderer.
- No package fragmentation — everything ships in the single public `streetui`
  package via its existing `.` / `./server` / `./testing` subpaths.
- The v1.0 frozen exports are not broken and no existing primitive is removed.
- The API is purely additive.

---

## 2. What shipped

### Core primitive (§3–§9, §13, §14)

- **`component(setup, { name? })`** → `ComponentDefinition<P>` — a pure factory
  (`__streetui_component: true`, `name`, `setup`). Building nothing by itself.
- **`container.component(key, def, props, children?)`** — materialises the
  reserved `'component'` graph node (rendered as a `<div>` wrapper, preserving
  the one-node/one-element positional-hydration invariant), runs `setup`
  synchronously at build time (like `errorBoundary`), and returns a render
  function that receives the component's own `ContainerDSL` scope.
- **`ComponentContext`** — `onCleanup(fn)`, `effect(fn)` (auto-disposed),
  `renderChildren(scope)` (native slots), stable `key`.
- **`isComponentDefinition(value)`** — runtime brand check.
- **Identity** is the author-supplied `key` (the build-order node id churns on
  list/branch rebuilds; the key does not).
- **Typed props** rely on TypeScript, not a runtime schema. `Signal` props drive
  fine-grained updates **without re-running `setup`**.
- **Lifecycle / cleanup** routes through a `__component__<id>` handler read at
  mount/hydrate → `NodeInstance.trackCleanup`; teardown runs children-first and
  the handler is pruned in `graph._unregisterNodeHandlers`.

### Ecosystem integration (§15–§20)

Because `setup` receives a normal `ContainerDSL` plus `ctx.onCleanup`, a
component can own overlays (dialog/popover/…), resources, forms, i18n, context
providers, and error boundaries with **no new render path** — each integration
is proven by a test that also asserts disposal on unmount. Router composition
(§16) is satisfied by construction: a component inside a route disposes when the
route unmounts, via the same mechanism as a `when` flipping false.

### DevTools (§21) & Testing (§22)

- `inspectComponents(graph)` → `InspectedComponent[]` (`id`, stable `key`,
  `name`, `depth`, `childCount`), in document order, reading only the public
  `data-streetui-component` attribute.
- `streetui/testing` adds `renderComponent`, `hydrateComponent`,
  `findComponent` / `findAllComponents` / `getComponentName`, and `trigger`.
  Deliberately omitted: `getComponentProps` (props are closure-captured, not
  reified on the node — a reader would lie) and `awaitResource` (`waitFor` /
  `flushUpdates` already settle async state).

### Docs (§23) & no-fragmentation (§24)

- Updated `docs/components.md` (first-class `component()` section),
  `docs/devtools.md` (`inspectComponents`), `docs/testing.md` (component
  helpers), and `CHANGELOG.md`. Everything is reachable via `npm install
  streetui`.
- No new package and no new subpath were introduced.

## 3. Performance & memory (§25–§26)

Mount → update → unmount → remount cycles at **50 / 100 / 200** iterations
(`packages/renderer/src/component-memory.test.ts`) prove there is no per-instance
leak. Rather than heap sampling — noise under happy-dom, and no browser is
available — the test uses **deterministic structural assertions**:

- every `ctx.onCleanup` fires **exactly once per unmount** (`cleanups === cycles`);
- the `setup` effect is torn down each cycle (`effectTeardowns === cycles`) and a
  post-final-unmount source change is **inert** (dead subscription);
- `setup` runs **once per mount** (`mounts === cycles`) — the in-cycle prop click
  updates fine-grained and never re-runs `setup`;
- `graph.handlerCount` returns to the **same baseline after every unmount** — the
  `__component__<id>` handler is pruned and does not accumulate across cycles.

Result: all three variants pass; no drift, no double-dispose, no missed dispose.

## 4. SSR byte-identity (§27)

Components render as a plain `<div data-streetui-component="Name">` wrapper on
the server, and the wrapper is a real semantic node (one node → one element), so
the server→client seam is unchanged. `node scripts/verify-ssr-hashes.mjs` →
**PASS**: all 5 routes are exact-equal to the recorded v1.6 SHA-256 digests
(overview 730B, dashboard 925B, users 3,610,699B, controls 36,551B, settings
926B). The component platform adds no byte to any existing route's output.

## 5. Additive API (§30)

Every addition is new surface; nothing existing changed shape or was removed:

```ts
// from "streetui"
component(setup, { name? }) : ComponentDefinition<P>
isComponentDefinition(value) : boolean
container.component(key, def, props, children?)     // ContainerDSL method
type ComponentDefinition<P>, ComponentContext, ComponentSetup<P>

// from "streetui/testing"
renderComponent(def, props, children?)
hydrateComponent(build, options?)
findComponent(container, name?) / findAllComponents(container, name?)
getComponentName(el)
trigger(el, type, init?)

// from "streetui/server" (devtools surface)
inspectComponents(graph) : InspectedComponent[]
```

The v1.0 frozen value/type exports are untouched; the per-package stability
tests still assert the frozen surface and pass.

intervening milestones did not refresh `bundle.json`. The component-only delta
therefore cannot be cleanly isolated from this measurement; this is disclosed
rather than attributed solely to components.
