## Summary

v1.8 set out to determine and improve StreetUI's real-browser **client**
behaviour (initial DOM creation, fine-grained updates, keyed lists, large-list
rendering, hydration, event handling, frame pacing, memory, bundle). The
mission's binding rule (§7/§10/§24) is that a client-renderer optimization may
ship **only** with real-browser evidence.

**A real browser is not available in this environment** and cannot be made
available: `npx playwright install chromium` fails with `403 Connection blocked
by network allowlist`, and no Chromium binary exists on `PATH` or via
`CHROMIUM_PATH`/`CHROME_PATH`. Therefore **no client optimization was shipped** —
doing so on Node/happy-dom evidence alone would violate the mission's honesty
contract.

What v1.8 *did* deliver, entirely within the "everything that does not require a
live browser" scope:

1. A **CPU-profile investigation** that honestly attributes JavaScript self-time
   and isolates the small StreetUI-controlled fraction, identifying `mountNode`
   as the top candidate for future browser-validated profiling (§6–§10).
2. A **genuinely complete + runnable browser/competitor harness**: the §26
   orchestrator now actually spawns and aggregates all three real sub-runners, so
   real numbers appear the moment a Chromium exists (§5/§19/§26).
3. A **new Node-runnable regression test** pinning the §9 update-locality
   invariant (independent-of-N), filling a real coverage gap without adding any
   unrunnable "browser" test (§23).
4. Full re-verification that **SSR remains byte-identical and stable** (§22), the
   frozen v1.0 API is preserved (§24), and SSR machinery still tree-shakes out of
   client bundles (§18).

The coordinated version is **bumped to 1.6.1** (patch release): no public API
change, and the v1.8 development milestone work ships as a patch because it
touches only benchmarks, tests, and tooling — nothing in the public runtime.

## §6–§10 Client-JS investigation (Node + happy-dom — NOT a browser)

`benchmarks/profile-client-js.mjs` mounts the real 10k-row `/users` route 6×
under `--cpu-prof`; `benchmarks/profile-parse.mjs` buckets self-time by source.
Result (`benchmarks/results/v1.8/client-js-profile.txt`):

```text
total samples=8881  ~wall=11838ms  (1333us/sample)
  gc               ~50.5%   5978.4ms
  happy-dom        ~40.4%   4778.7ms
  streetui          ~7.2%    847.8ms
  node-core         ~1.4%
StreetUI-controlled fn self-time (the only bucket StreetUI owns):
  mountNode        ~4.5%    531.9ms
  applyNodeProps / dispose / createNode / setAttribute / applyProp …  <0.4% each
```

**Honest interpretation.** In this Node run, wall time is dominated by GC (~50%)
and happy-dom's pure-JS DOM emulation (~40%). happy-dom's
`createElement`/`appendChild`/`setAttribute` are **native** in a real browser, so
that ~40% is **not** a StreetUI cost and **not** a browser proxy. GC pressure and
sampling behaviour under Node likewise do not represent a browser. The only
StreetUI-controlled slice is ~7.2%, within which **`mountNode`** (the recursive
per-node create → `applyNodeProps` → one `NodeInstance` allocation →
`ctx.instances.set` → wire → recurse → `appendChild` walk) is the single largest
function.

**Candidate identified, optimization deferred.** `mountNode` (initial creation +
one `NodeInstance`/Map entry per node) is the top candidate for future work, and
the ~50% GC share is *consistent with* allocation being the axis that matters —
but **§10 forbids shipping a client optimization without real-browser evidence**,
and none is available. So v1.8 ships **no** `mountNode` change: the candidate is
documented for a browser-validated follow-up, not acted on speculatively. This is
exactly the §24 outcome that accepts "profiling proves the remaining measurable
cost is browser-native rather than StreetUI-controlled".

## §9 Reactive update locality — invariant PINNED (Node-testable)

The browser wall-clock scenario (1/10/100 changed of 1k/10k controls) is BLOCKED,
but the load-bearing *structural* guarantee is engine-independent and now has a
dedicated regression suite: `packages/renderer/src/update-independence.test.ts`
(4 tests, all pass). Counting every DOM write through the same `DOMAdapter`
choke-point the renderer uses, it asserts:

- updating **one** of N bound signals ⇒ exactly **1** `setTextContent`, **0**
  create/append/insert/remove — verified identical at **N = 100 and 1000**;
- the single-update write total does **not** grow with N (equal at N=100 vs
  N=2000);
- updating **K** distinct signals ⇒ exactly **K** writes at N=5000;
- setting a signal to its current value ⇒ **0** writes.

This complements the existing `run-streetui.mjs` gate
(`fine_grained_update_independent_of_N`: toggle 1/1000 = 2 writes vs 1/100 = 2
writes) with unit-level coverage. No happy-dom timing is presented as a browser
number.

## Known limitations

- **No client optimization shipped** — by design, absent real-browser evidence
