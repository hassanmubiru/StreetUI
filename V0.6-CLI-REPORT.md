# StreetUI v0.6 — Developer Experience, CLI & Project Tooling

This report documents v0.6, whose single goal is that a new developer can go from
nothing to a running StreetUI app:

```
npm create streetui@latest my-app
cd my-app && npm install
npm run dev      # working app in the browser
npm run build    # production build → dist/client + dist/server
npm run start    # serve the production build (SSR + hydration)
```

The CLI **orchestrates** the existing pipeline (`DSL → Compiler → Graph → Runtime →
Renderer`). It is not a new framework layer, introduces no second reactive system,
and does not rewrite the compiler.

success.

## CLI

The `streetui` binary exposes exactly the behaviour it advertises; unknown options
are rejected rather than silently ignored.

- **`create <dir>`** — scaffolds a real, working StreetUI app (no placeholder code,
  no fake APIs, no React, no JSX). Two templates: `ssr` (default) and `basic`.
  Refuses to write into a non-empty directory; rejects unknown template names.
- **`dev`** — builds once, then watches with esbuild's incremental `context()`
  rebuild (only what changed is recompiled), injects a small SSE live-reload
  snippet, and prints the URL once the server is actually listening. Build errors
  are printed with real source positions and never crash the server.
- **`build`** — two esbuild passes → `dist/client/main.js` (+ copied public assets)
  and `dist/server/server.js`. Fails (non-zero exit) only on real errors;
  third-party warnings are non-fatal. Server pass is skipped for client-only apps.
- **`start`** — serves the build with Node's `node:http` (no Express, no
  third-party server). Static assets under `dist/client/` are served by extension;
  every other request is server-rendered through `server.js`. Builds first if no
  build exists.
- **`--help` / `-h`** — prints the command/option reference.
- **`--version` / `-v`** — prints the CLI version.

## Generated project

Verified against the **actual** generated template (not helper stand-ins) by
`e2e.test.ts`: create → link built workspace packages → `buildProject('production')`
→ `startServer` → real `fetch`.

- **Build** — the scaffolded app builds to `dist/client/{main.js, styles.css,
  favicon.svg}` and `dist/server/server.js`.
- **SSR** — `GET /` returns `200 text/html` containing `id="app"`, the project
  brand, a `data-streetui-state` hydration island, and `src="/main.js"`. `GET
  /about` returns different server-rendered HTML (view switching via a `when()`
  signal). `GET /main.js` returns `200` with a JavaScript content type and a
  non-empty body.
- **Hydration** — `main.ts` reads the state island, seeds the signals with the
  exact server values, recompiles the same app, and calls `renderer.hydrate`, so
  the server markup is adopted rather than discarded.

## Dependencies added

One runtime dependency, in `@streetui/cli` only:

- **`esbuild` 0.24.2** — the bundler used for `dev`/`build` and for compiling
  `streetui.config.ts` on the fly. Justified: it is the build tool itself, and
  `tsup` (already in the toolchain) uses it transitively. No other runtime
  dependency was added anywhere; the server uses only Node built-ins (`node:http`,
  `node:fs`, `node:path`, `node:url`).

## Two correctness bugs found and fixed

Both surfaced while verifying the real generated-project pipeline (recorded in
memory as `streetui-cli-build-traps`):

1. **Warnings treated as fatal** (`build.ts`) — esbuild `result.warnings` (e.g.
   dependency `package.json` exports-ordering notes) were folded into fatal
   problems, so the build produced valid bundles but exited 1 and skipped copying
   public assets. Fixed: only real errors from the `.catch()` branch are fatal.
2. **Compiled config unresolvable** (`config.ts`) — the on-the-fly-compiled
   `streetui.config.mjs` was written to the OS temp dir, where its external
   `@streetui/cli` (`defineConfig`) import could not resolve. Fixed: the temp
   `.mjs` is now written next to the config file so bare imports resolve against
   the project's `node_modules`.

## Known limitations

- The `@streetui/*` packages are **not yet published to npm**. Inside this
  monorepo a generated app resolves them through the workspace (the e2e test links
  them); `npm create streetui@latest` is the intended public entry point once the
  packages are published (publishing metadata is prepared, not executed).
- Starter templates switch views with a `when()` signal rather than the router, to
  keep SSR + hydration identity robust; the router-outlet path re-renders route
  content on hydration and is left for URL-driven apps that opt in.
- **Streaming SSR is not implemented** — `renderToString` produces the full
  document in one pass.

## Future work

## Scope discipline

Per the v0.6 stop condition, this release intentionally does **not** include: a
full devtools UI, a performance optimizer, a compiler rewrite, a component library,
animation, streaming SSR, or a new state-management system. The architecture
remains `DSL → Compiler → Graph → Runtime → Renderer`; the CLI only orchestrates
it. v0.6 is complete and verified — v0.7 has not been started.
