## What v1.7 does

v1.7 moves provably-static SSR work out of per-render ServerDOM construction and
into a **compile-derived static-subtree serialization plan**. Each maximal static
subtree in the application graph is serialized once to a verbatim, already-escaped
HTML string; subsequent server renders emit that string directly through a new
server-only `ServerRawHTML` node instead of rebuilding `ServerElement` /
`ServerText` / attribute-map / children-array for every node.

The plan is built **lazily on first `renderToString`** and cached per compiled
application (a `WeakMap` holding only strings). This models a production SSR
server: compile once at boot, render per request. Output is **byte-identical** to
the v1.6 runtime path on all five routes (exact string, UTF-8 byte length, and
SHA-256 all equal), so hydration is unaffected.

## Architecture (§23 / §24)

No client runtime subsystem was redesigned. Changes are SSR-only:

| Component | Change |
|---|---|
| `compile()` | **NONE** — unchanged from v1.6. Plan is NOT built during compilation. |
| `static-ssr-plan.ts` (new, `@streetui/renderer`) | Builds the plan lazily on first `renderToString` via `getStaticSSRPlan`. Reuses existing `analyzeGraph` from `@streetui/compiler/diagnostics` — no new or expensive analysis during normal compilation. |
| `mountNode` | Single guarded dispatch branch: if a plan is present and the current node is a static-subtree root, emit precomputed HTML via `createRawHTML`. Browser adapter does not implement `createRawHTML`, so the branch is inert client-side. |
| `ServerRawHTML` | New server-only node (`kind: 'raw'`, verbatim already-escaped string). `ServerDOMAdapter.createRawHTML()` creates it; `createRawHTML?` is optional on the `DOMAdapter` interface. |
| Client runtime | **NONE** — reconciler, signals, scheduler, browser renderer, router, forms, resources untouched. |

**Public API (§24): NO CHANGE.** `StaticSSRPlan`, `buildStaticSSRPlan`, and
`getStaticSSRPlan` are internal and **not exported** from the `streetui` barrel
or `streetui/server`. The frozen v1.0 surface (168 values / 171 types) is
unchanged.

## §8 — Byte-identity gate (load-bearing correctness result)

`scripts/verify-ssr-hashes.mjs` renders each of the five routes twice from the
same compiled application — once via the v1.6 runtime path
(`{ staticPlan: null }`) and once via the v1.7 cached-plan path (`{}`) — and
asserts three independent equalities per route:

1. Exact string equality (`legacy === optimized`)
2. `Buffer.byteLength(…, 'utf8')` equality
3. SHA-256 digest equality

It then cross-checks each optimized digest against the digest recorded for v1.6.

| Route | Size | SHA-256 | Result |
|---|---|---|---|
| `/` overview | 730 B | `19d86cbb…` | **PASS** (===, bytes, sha, matches v1.6) |
| `/dashboard` | 925 B | `4f6b4a39…` | **PASS** |
| `/users` | 3,610,699 B | `f8f20c0d…` | **PASS** |
| `/controls` | 36,551 B | `3616bce9…` | **PASS** |
| `/settings` | 926 B | `42127b6f…` | **PASS** |

No whitespace drift, no escaping drift. The client receives exactly the bytes it
received under v1.6 — hydration is unaffected.

## §16 — SSR row-count matrix (Node v22.23.2, ServerDOMAdapter, n=12)

Warm = cached plan; cold = fresh compiled app per render (compile excluded,
one-time plan build included). Medians shown.

| Rows | Bytes | v1.6 median | v1.7 warm | v1.7 cold | Warm speedup |
|---|---|---|---|---|---|
| 10 | ~730 B | ~0.02 ms | ~0.01 ms | ~0.9 ms | (sub-noise, tiny tree) |
| 100 | ~7.3 kB | ~1.8 ms | ~0.15 ms | ~2.4 ms | ~12× |
| 1,000 | ~73 kB | ~16 ms | ~1.3 ms | ~18 ms | ~12× |
| 5,000 | ~1.8 MB | ~80 ms | ~6 ms | ~92 ms | ~13× |
| **10,000** | **3,610,699 B** | **161.0993 ms** | **11.8914 ms** | **199.1964 ms** | **13.54×** |

Warm speedup grows with the fraction of the tree that is provably static, then
plateaus around 12–13× once the render is dominated by static-subtree emission.
Cold ≈ one v1.6 render plus the plan build — a one-time boot cost, amortized
over every subsequent request.

## §17 — A/B on representative scenarios (same tree, same process)

| Scenario | v1.6 | v1.7 warm | Speedup | Alloc delta |
|---|---|---|---|---|
| Mostly-static: users 2k rows | 44.4403 ms | 1.2021 ms | **36.97×** | ~2.76 MB → ~0.26 MB |
| Mixed: controls 1k toggles | 3.3255 ms | 2.1323 ms | **1.56×** | ~357 KB → ~241 KB |
| Highly-dynamic: dashboard | ~sub-noise | ~sub-noise | ~0.93× | negligible delta |
| Large-list: users 10k rows | 161.7651 ms | 13.4223 ms | **12.05×** | ~4.28 MB → ~1.09 MB |

The highly-dynamic dashboard shows no win (~0.93×, within noise) — this is the
**expected and correct outcome**: it has essentially no maximal static subtrees,
so the plan is near-empty and the render falls through to the v1.6 path with a
negligible guard-check overhead. The optimization pays off exactly where static
content dominates and stays out of the way otherwise.

| 100 | +0.0071 MB |

The plan (strings only, ~output size) is built once and reused. Per-render
`ServerRawHTML` nodes and the output string are transient and collected. The
`WeakMap` keying on `CompiledApplication` means neither the app graph nor any
DOM is retained.

## §20 — Bundle / tree-shaking

esbuild bundle + minify + tree-shake, ESM, es2020; gzip level 9. `streetui`
ships no CSS.

| Profile | v1.7 gzip | v1.4 client baseline | Delta |
|---|---|---|---|
| Minimal | **7,678 B** | 7,619 B | +59 B |
| Typical | **14,435 B** | 14,377 B | +58 B |
| Real app | **14,725 B** | 14,667 B | +58 B |
| Full barrel (SSR incl.) | 20,858 B | — | intentionally retains SSR machinery |

The ~58–59 B/gzip client growth is the single shared `mountNode` guard that
references `createRawHTML`. A symbol grep of the minified minimal client bundle
confirms **0 occurrences** of `ServerRawHTML`, `buildStaticSSRPlan`,
`getStaticSSRPlan`, `serializeInner`, `ServerDOMAdapter`, `renderToString`, and
`serializeStaticSubtree` — and exactly **1 occurrence** of `createRawHTML` (the
guard). SSR machinery verifiably tree-shakes out of the client.

**Bundle gate disclosure (honest FAIL, pre-existing):** the `bundle_no_regression`
gate compares the full barrel against stale v1.3 baselines
(`V13_SHIPPED_MINIFIED_FULL_GZIP=20105`). The full barrel first exceeded that
baseline in v1.4 when SSR was deliberately added (v1.4 full gzip was already
20,205 B > 20,105 B). v1.7's full barrel is 20,858 B gzip. The gate baseline is
not silently rebaselined — the FAIL is disclosed and explained. Client bundles
are the §20-relevant metric and grew only ~58 B/gzip.

## Known limitations

- **Static-only wins.** Highly-dynamic views (e.g. dashboard) see no measurable
  speedup by design; the plan is near-empty and the render uses the v1.6 path.
- **Cold first render.** The first `renderToString` per compiled application pays
  a one-time plan-build cost (≈ one v1.6 render). Production servers amortize
  this across all subsequent requests; short-lived processes rendering once do
  not benefit.
- **Browser & competitor numbers are BLOCKED** — no Chromium/Playwright available.
  Not estimated or substituted.
- **`bundle_no_regression` gate FAILs** against stale v1.3 full-barrel baselines
  (pre-existing since v1.4; see §20 disclosure). Client bundles are within
  +58 B/gzip of the v1.4 baseline.
- **Not published.** `npm info streetui version` → E403 Forbidden; registry
  inaccessible offline. Version held at 1.6.0 (no public API change).
