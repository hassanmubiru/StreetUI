## 1. What 2.0 is

StreetUI 2.0 makes the framework feel *complete* for building serious
applications, without adding a second reactive system, a virtual DOM, a second
renderer, or any React/Vue compatibility layer. Every capability below ships
additively on the existing DSL → Compiler → Semantic Graph → Runtime → Renderer
pipeline and through the single public `streetui` package.

The 2.0 surface (all reachable from `streetui`, `streetui/server`, `streetui/testing`):
data mutations (`mutation`, `createClient`, `HttpError`, `createAuthSession`),
first-class components (`component()`), per-route/document `head` metadata
(`page.head` + server `renderHead`), async & error UI boundaries
(`asyncBoundary`, `errorBoundary`), overlays (dialog/popover/tooltip/dropdown/
toast) with portalling + focus management, a CSS-class transition engine,
accessibility platform (keyboard nav, live regions, focus-owner, deterministic
a11y ids), production error diagnostics, headless DevTools inspectors, and
testing helpers.

## 3. Audits (§22 / §23 / §28) — additive-only, single-package

- **Additive API (§22/§28).** Each package's `public-api.stability.test.ts`
  asserts every FROZEN export is *present* (`for (name of FROZEN) expect(name in
  API)`), not set-equality — so additions pass and only removals/renames fail.
  All stability tests pass ⇒ nothing was removed or renamed; the 2.0 surface is
  provably additive over 1.x.
- **Single public package (§23).** `streetui`'s `exports` map is exactly `.`,
  `./server`, `./testing`, `./package.json`. Its only runtime dependency is
  `esbuild` (bundled-CLI build); no `@streetui/*` runtime deps (all inlined via
  tsup). No new public subpath was added in 2.0.
- **New 2.0 exports flow through the barrel.** `mutation`, `createClient`,
  `HttpError`, `createAuthSession`, `component`, `renderHead`, and the DSL
  container methods (dialog/popover/tooltip/dropdown/toast/asyncBoundary/
  errorBoundary/transition/head) all reach consumers via `export *` and are

## 5. Honestly BLOCKED (§24) — not faked

- **npm publish:** BLOCKED — registry returns `E403 Forbidden`; nothing
  published. The release is *packable* and *release-check-clean*, but the
  publish step itself did not run. No "published" claim is made.
- **Full consumer-smoke (main barrel):** BLOCKED — the public `streetui`
  package's third-party runtime dependency `esbuild@0.24.2` (and its native
  `@esbuild/linux-x64` platform binary) is not present in the offline npm HTTP
  cache, so an offline install that includes the main barrel cannot resolve it.
  This is a pre-existing *environment* blocker (no registry access), independent
  of the 2.0.0 bump — it fails identically at 1.9.0. The esbuild-free framework
  consumption path is proven above.
- **Browser / assistive-technology conformance:** BLOCKED — no Chromium/
  Playwright (403 allowlist). Tests run against happy-dom, which models the DOM
  but not an AT. No WCAG/APG conformance pass is claimed.
- **Competitor ranking:** competitors are installed and exercised for Node SSR/
  bundle only; no browser ⇒ **not ranked**.
