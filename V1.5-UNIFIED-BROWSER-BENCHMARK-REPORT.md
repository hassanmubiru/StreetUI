### §2 reporting accuracy (corrected to executed reality)

The brief asks for this exact framing:

```text
framework tests passed:            612
known pre-existing example failures: 7
new framework failures:              0
```

Those numbers are **not what the suite produces**. The executed suite reports:

```text
framework tests passed:            657   (VM, Node v22.23.2)   /  655 (host, Node v24.18.0)
known pre-existing example failures:  0
new/observed example failures:        0   (VM)                 /    2 (host, example-account)
```

The specific "612 / 7 live-HTTP" figures were fabricated in a prior report
revision — the count `7` and the browser-regression millisecond figures have
never been produced by an executed run here. **However**, an earlier draft of
this report over-corrected by asserting the `example-account` / `example-data`
live-HTTP failures "do not exist" and that "those directory names belong to a
different project." **That was wrong and is retracted.** StreetUI genuinely
contains `@streetui/example-account` and `@streetui/example-data`, both with real
live-HTTP tests. A re-run on the user's host (Node v24.18.0, 2026-09-25) failed
**2** of them:

```text
FAIL examples/streetui-account/src/account-app.test.ts
  account app — resources (plans)
    × loads plans from the real API and renders them   (expected '' to be 'Free')
    × shows an error + retry when the plans request fails
Tasks: 45 successful, 47 total   (Failed: @streetui/example-account#test)
```

**Root cause (code-level, controlled):** both failing tests wait a fixed
`tick(40)` (40 ms wall-clock) for a `resource(() => fetchPlans(...))` that fires
an async fetch against a real localhost HTTP server on mount, then assert the
plans list rendered — **without ever awaiting the fetch's resolution**. The
example exposes an `onPlansResource` hook (`account-app.ts:244`) the test could
await, but the test ignores it and sleeps instead. By contrast, the *forms*
tests in the same file `await form.submit()` (awaiting the real promise) and
**pass**. So this is a wall-clock race in the example test, not a StreetUI
runtime defect: 40 ms was enough on the VM's Node 22 but not on the host's
Node 24. Per the mandate I do **not** label it a framework regression — it has
not been reproduced under controlled conditions here (the VM runs Node 22, where
it passes), and every signal points to example-test timing flakiness. The clean
fix is to await `onPlansResource` (mirroring the forms tests) or poll until the
list populates, rather than a fixed 40 ms sleep.

## SSR (§13–§14) — profiled in Node

SSR ran (it needs no browser). `renderToString` for `/users` (10k rows):

| Metric | Value |
|---|---|
| SSR render `/users` (renderToString) | median **199.8 ms**, p95 234.2, min 180.4, max 234.2, n=15 |
| Phase split | **mount 60.1%** (120.1 ms) + **serialize 31.5%** (62.9 ms) + remainder |
| Serialize A/B (same tree, same process) | legacy 107.4 ms → shipped **65.7 ms = 1.63× faster**, byte-identical |
| Per-text-node escape share | **3.4%** of render (70,021 text runs, 0 containing special chars) |

**§13/§14 finding:** the remaining SSR cost is **mount-dominated** (building the
ServerDOM tree ≈ 60%), not serialization or escaping. The v1.4 serializer
fast-path is confirmed (1.63×, byte-identical). A compiler-aware static SSR path
that skips intermediate server-node construction for static subtrees is the
justified next target — **but** the escape microbench also shows a trap: a
whole-body escape "fast path" is *slower* (29.9 ms) than the shipped per-node
path (15.2 ms), so the static-path work must be profiled per-node and gated on a
byte-identity check before shipping. No speculative SSR rewrite is shipped in
v1.5 on the strength of a microbench alone.

## Methodology

Node/happy-dom timings use `perf_hooks`; each scale-sensitive scenario runs in
its own child process so the 10k-row cases (~0.8 GB of happy-dom nodes) cannot
accumulate across scenarios. DOM mutations are counted at the single
`BrowserDOMAdapter` choke point, so "toggle 1 of 1000 touches 2 nodes" and
"typing one field does not touch another" are **measured, not assumed**. Timed
scenarios report median/p95/min/max/sample-count with ≥12 reps for mount &
hydration and ≥10 for router (§1). The unified browser runner
(`benchmarks/browser/run-all.mjs`) proves Chromium + Playwright + each framework
are present **before** claiming any number, and writes `BLOCKED` with the exact
reason otherwise. **No number in this report crosses environments** — no
happy-dom value is presented as, or compared against, a browser value.
