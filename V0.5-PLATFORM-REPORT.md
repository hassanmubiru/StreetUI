# StreetUI v0.5 — Application Platform

**Architectural report**

v0.5 makes StreetUI suitable for complete production applications by adding seven
capabilities — forms, form state, validation, submission lifecycle, context,
accessibility primitives, and internationalization — **without** introducing a
second state system, a virtual DOM, a component library, or any third-party
runtime dependency. Every new capability is built on the primitives that already
exist: `@streetui/state` signals, the DSL's attribute/event/binding API, the
compiler → graph → renderer pipeline, and the SSR + hydration machinery from
v0.4.

---

## What shipped

| Capability | Package / location | Built on |
|---|---|---|
| Reactive form model + state | `@streetui/forms` (`createForm`) | `signal` / `derived` / `batch` |
| Validation | `@streetui/forms` (`required`, `minLength`, `maxLength`, `email`, `pattern`, custom) | plain `(value) => string \| undefined` |
| Submission lifecycle | `@streetui/forms` (`form.submit()` / `status`) | signals + existing submit-event `preventDefault` |
| Context | `@streetui/context` (`createContext`) | synchronous build-time value stack |
| Accessibility ids | `@streetui/core` (`a11yIds`) | deterministic string derivation |
| ARIA / role / tabindex | DSL attribute API (existing) | `applyProp` / `applyA11yProps` |
| Internationalization | `@streetui/i18n` (`createI18n`) | `signal` / `derived` + `Intl.PluralRules` |
| Integration app | `examples/streetui-account` | all of the above + router + resources + SSR |

## Design decisions and their rationale

**Forms reuse the one input binding.** A field's `value` is a writable
`Signal<string>` passed straight to `input({ bind })`. The renderer already wires
that binding bidirectionally, so no duplicate event listeners are added: user
typing and programmatic `setValues()` flow through the same channel. `values`,
`errors`, `touched`, `dirty`, `valid`, and `status` are all derived signals, so
a single field change recomputes only the derivations that read it — the whole
app does not re-render (§37). `setValues()`/`reset()` run inside `batch()` and a
`programmatic` guard so bulk updates don't spuriously mark fields touched and
flush once.

**Validation stays synchronous.** A `Validator` is `(value) => string |
undefined`; per-field validators run in order, first error wins. This keeps
`form.valid` a pure synchronous derivation — predictable and SSR-safe. Async
validation is documented as a layering on top via `resource()`, deliberately
outside the core so network latency never destabilises `valid`.

**Context is a build-time stack, not React Context.** StreetUI builds its
semantic tree synchronously top-down; `provide(value, run)` pushes for the
duration of `run()` and pops in `finally`, so nesting resolves to the nearest
provider and nothing leaks after the builder returns. The context holds no
subscriptions — reactivity, when wanted, lives in a signal placed *into* the
context and is torn down by the normal node lifecycle.

**Accessibility is cross-cutting, not a new API.** ARIA/`role`/`tabindex` ride
the existing attribute passthrough; ARIA booleans serialize as `"true"`/`"false"`
strings so they survive SSR and hydration. The only genuinely new surface is
`a11yIds()` in core — and it uses **no counter and no randomness**, deriving ids
purely from a stable base string. That is what makes label/description
relationships identical on server and client and safe across re-rendered
`when()` branches.

**i18n is deterministic for SSR.** The active locale is a signal; `t()`/`plural()`
are derived signals that recompute on `setLocale()`. A missing key echoes the key
itself and `(locale, key, params)` is a pure function, so `renderToString()` and
`hydrate()` agree byte-for-byte as long as the client boots with the server's
locale. Pluralization is delegated to `Intl.PluralRules`, so locale rules need no
custom tables.

## The integration app (§33) and its one honest limitation

`examples/streetui-account` renders on the server and hydrates on the client with
the **same build function**. During hydration the persistent shell (nav, brand)
adopts the exact server DOM nodes — verified by node identity. The **route-outlet
content** is re-rendered fresh on first hydration rather than adopted node-for-node;
this is pre-existing `@streetui/router` behavior (its own hydrate test asserts
only shell node identity plus route `textContent`), confirmed with a minimal
two-route probe independent of the account app. The integration test therefore
asserts what actually holds and matters: shell node adoption, **no duplication**
of the deterministic a11y markup (each id present exactly once), server markup
carrying the correct a11y attributes, post-hydration content correctness, and
live client navigation afterward. Router internals were left untouched to protect
the baseline; making route-content adoption node-identical is a candidate for a
future router revision, not a v0.5 change.

## Constraints honored

No React/Vue/Preact/JSX/vdom (§35–36); no new runtime dependencies (§39, `Intl`
is a platform built-in); no fake APIs in the example (§34, real `node:http`
server); a single field change does not re-render the app (§37); all new
packages export cleanly from their `index.ts` and every public API is documented
in package READMEs and the root README (§38, §40). TypeScript-first throughout —
no `any` in the public form value/validator/i18n key surfaces.

**Stop condition:** v0.5 is complete and the entire repository verifies. Work
stops here — v0.6 is not started.
