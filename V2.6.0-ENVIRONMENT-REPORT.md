# StreetUI 2.6.0 — Environment Report

**Phase 10 of the 2.6.0 "Production Website Validation" mission.** This report records,
honestly and in full, the environment in which the 2.6 validation work was performed, so
that every "PASS", "BLOCKED", and "not measured here" claim in the other 2.6 reports can
be read against the capabilities that were actually present.

The governing rule for this mission: **sandbox-absence is not fabrication, and
fabrication is not permitted.** Where a gate could not run because the capability does not
exist in this environment, it is marked **BLOCKED (sandbox)** and attributed to the
authoritative environment — never silently passed, never given invented numbers.

---

## 1. Two environments

StreetUI is validated across two distinct environments. They are not the same machine and
must not be conflated.

**(A) This sandbox** — a lightweight Linux VM used for all code, test, build, SSR, and
bundle work in this session. It has Node and the repo, but no browsers, no assistive
technology, and no reachable npm registry.

**(B) The authoritative environment** — a separate, user-confirmed machine that owns
Chrome 154, Firefox 155, Orca + AT-SPI, and an authenticated npm registry, and from which
2.2.0 and 2.3.0 were actually published. Browser-rendered performance, axe-core visual
checks, real screen-reader (AT) runs, offline/online package installation against the
registry, and the publish step are **owned by (B)** and are out of scope for anything
measured in (A).

The authoritative artifacts already in-repo from (B) are evidence of this split: e.g.
`benchmarks/results/v2.5/accessibility-at.json` records `orca` at `/usr/bin/orca` version
`46.1` with a live a11y bus, and `benchmarks/results/v2.5/visual-a11y.json` records
`chromium` `154.0.8037.57`. Neither tool exists in this sandbox (see §2); those files were
produced in (B) and must not be overwritten from (A).

## 2. Sandbox capability probe (measured this session)

```
node   : v22.23.2
npm    : 10.9.8
os     : Linux 6.8.0-138-generic
chrome : NONE          (google-chrome / chromium / chromium-browser all absent)
firefox: NONE
orca   : NONE
pnpm   : NONE
npm registry reachable : NO  (npm ping → error)
```

Consequences, each of which gates a specific class of claim:

- **No browser** → no FCP/LCP/CLS/TTI, no real paint timings, no axe-core-in-page run.
  Phase 2 (website performance) and the VISUAL layer of Phase 3 (accessibility) are
  BLOCKED here.
- **No Orca / AT-SPI** → the ASSISTIVE_TECHNOLOGY layer of Phase 3 is BLOCKED here.
- **No reachable registry** → `npm publish` and any registry-backed `npm install` are
  BLOCKED here. (Clean-room execution of the *packed* artifact is still possible and was
  done — see §4.)
- **No pnpm** → the monorepo's native package manager is absent; a shim is used (§3).

None of these absences is a framework or website defect. They are properties of (A).

## 3. Build / test / SSR workarounds used (and why each is sound)

**pnpm shim + local `.bin` on PATH.** The repo is a pnpm workspace, but pnpm is absent.
`turbo` is driven with `PATH="/tmp/shim:<repo>/node_modules/.bin:$PATH"`, where
`/tmp/shim/pnpm` is an exit-0 stub. Turbo resolves `@streetui/*` to **source** and the
website resolves `streetui` to the **built dist**, exactly as in a real consumer; the shim
only prevents turbo from shelling out to a package manager it does not need for these
tasks.

**Website vitest run directly.** The website suite is run from
`examples/streetui-website/` with `PATH="$PWD/node_modules/.bin:$PATH" vitest run`.

**SSR byte-identity gate module resolution.** `scripts/verify-ssr-hashes.mjs` imports bare
`happy-dom` and `streetui`, which do not resolve from `scripts/` in the pnpm layout. It is
copied into `examples/streetui-performance-app/` (whose `node_modules` symlinks
`happy-dom` and `streetui`) and run with `W=<repo root>` so it reads the real golden
baseline. The gate measures everything **in-process**; no network, no browser.

**Tarball packing / clean-room.** `scripts/pack-tarballs.mjs` is run from `/tmp` so its
output directory is a writable VM path (the mounted workspace forbids `unlink`, so an
existing `dist-tarballs/` cannot be replaced in place). The packed tarball is then
extracted and executed in a clean `/tmp` directory (§4 of the release report).

**Undeletable mount files.** Files under the mounted workspace cannot be `rm`-ed
("Operation not permitted"); `allow_cowork_file_delete` reports "Could not find mount for
path". They **can** be truncated/overwritten. Two leftover temp scripts
(`examples/streetui-performance-app/_verify_ssr_gate.mjs` and the earlier
`_route-hash-tmp.mjs`/`_verify-ssr-tmp.mjs`) were therefore overwritten to inert
`export {};` stubs rather than deleted; none sits under a `tsconfig` `include` glob
(`src/**/*` only), so none affects build or typecheck. The vestigial
`examples/streetui-website/src/_dbg.test.ts` is likewise undeletable; it holds the real
metadata pure-function unit suite and should be renamed to `metadata.test.ts` in (B).

**esbuild offline-install limitation.** The unified `streetui` package declares
`"dependencies": { "esbuild": "0.24.2" }` for its bundled CLI bin. Offline `npm install`
of the tarball in (A) fails because esbuild's platform binary is not cached and the
registry is blocked. This is a **sandbox network limitation, not a packaging defect**: the
framework's import/require path does not touch esbuild, which is why clean-room execution
of the extracted artifact succeeds (§4 of the release report). Registry-backed install is
owned by (B).

## 4. What this environment could and could not establish

**Established in the sandbox (real, in-process, this session):**
monorepo build 30/30, typecheck 48/48, test 48/48; website vitest 58/58; public-API
version pin held at 2.5.0 (framework and CLI); SSR byte-identity 5/5 routes exact and
equal to the v1.6 golden; client bundle leak-check CLEAN; clean-room execution of the
packed ESM and CJS artifacts.

**BLOCKED in the sandbox (owned by the authoritative environment, recorded not faked):**
browser-measured website performance (FCP/LCP/CLS/TTI); axe-core VISUAL checks; real
Orca + AT-SPI ASSISTIVE_TECHNOLOGY runs; registry-backed `npm install` and `npm publish`.

The companion `benchmarks/results/v2.6/website-performance.json` and
`benchmarks/results/v2.6/accessibility.json` carry `status: "BLOCKED_SANDBOX"` with no
numeric fields, precisely so that no reader can mistake an absent measurement for a
passing one.
