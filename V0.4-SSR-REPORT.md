## 1. Overview

v0.4 makes StreetUI a *universal* framework: one semantic definition
(DSL → Compiler → Graph) is rendered to an HTML string on the server and
*adopted* — not rebuilt — in the browser. The public surface added is
deliberately small: `renderToString`, `hydrate` (as a method on the existing
renderer), and the `serializeState` / `readState` state-transfer pair. Router
and `resource()` gain thin hydration hooks (`mountRouter({ hydrate: true })` and
resource seeding), reusing machinery that already existed.

The defining constraint held throughout: **no second renderer and no virtual
DOM.** Server and client run the identical `mountGraph` pipeline; the only new
abstraction is a second `DOMAdapter` implementation.

## 2. Architecture & key design decisions

The pipeline is unchanged — `DSL → compile() → CompiledApplication{graph} →
renderer`. Server rendering and hydration are two new *entry points* into the
same renderer, not new renderers:

```
                       ┌── mount(compiled, container)   → cold browser render
compile(app) ─ graph ──┼── hydrate(compiled, container) → adopt server DOM
                       └── renderToString(compiled)     → HTML string (ServerDOMAdapter)
```

The decisive design choice is the `DOMAdapter` seam. Every DOM operation in the
renderer (`createElement`, `setTextContent`, `setAttribute`, `appendChild`,
`tagName`, `querySelector`, …) goes through an adapter interface. Two
implementations exist:

- **`BrowserDOMAdapter`** — delegates straight to real `document` APIs.
- **`ServerDOMAdapter`** — a lightweight in-memory node tree that serializes to
  an HTML string.

Because the mount logic is written against the interface, `renderToString` reuses
`mountGraph` verbatim; there is no SSR-specific rendering path to drift out of
sync with the browser path. This is why server and client markup are structurally
identical by construction — the precondition that makes positional hydration
sound.

## 3. Server rendering — `renderToString` (spec §2, §3, §4)

`renderToString(compiled, { domAdapter? })` creates a `ServerDOMAdapter`, builds
a synthetic container, runs `mountGraph`, serializes the container's *inner* HTML
(the app's own elements only — the synthetic wrapper is not emitted), then
disposes. It touches no browser globals: there is no `window`, `document`,
`HTMLElement`, `Node`, `location`, or `localStorage` reference on the server path
— all access is mediated by the adapter, so the module imports cleanly under
plain Node.js.

Serialization details that matter for hydration correctness:

- **Void elements** are emitted HTML5-style — `<img src="…">`, `<input …>` —
  with no self-closing slash and no closing tag (a browser parses these
  identically, so adoption matches).
- **Text and attribute values are escaped**, making the output XSS-safe by
  construction.

## 4. Hydration — matching & recovery (spec §5, §6)

`renderer.hydrate(compiled, container)` calls `hydrateGraph`, which walks the
graph top-down against the existing server DOM. Each graph node is matched
**positionally** to one element by expected tag
(`ctx.dom.tagName(el) === expectedTag(node)`):

- **Match** → the existing element object is *adopted in place*. Behavior is
  attached to it (see §5) — the node is never deleted and recreated.
- **Local mismatch** (e.g. the server emitted `<h1>` where the client graph now
  expects `<p>`) → `mountFreshAt` rebuilds only that one subtree at its position;
  the surrounding app is untouched, so a single divergence never triggers a
  whole-tree teardown.
- **Surplus** server DOM beyond what the graph describes is removed.

Because matching is positional and tag-based, `resetIdCounter` parity between the
server and client renders is **not** required — a freeing observation that
removes a whole class of hydration-mismatch bugs other frameworks suffer from.
`runtime.hydrate` uses `this._renderer.hydrate ?? this._renderer.mount`, so a
renderer without hydration degrades gracefully to a cold mount rather than
throwing.

## 5. Behavioral hydration — events, reactivity, lists, inputs (spec §7–§12)

Adoption reuses the *same* browser behavioral helpers the cold mount uses
(`wireEvents`, `wireSignalBindings`, `wireReactiveList`, and the per-node update
functions `textUpdate` / `headingUpdate` / `inputUpdate` / `buttonUpdate`), so
post-hydration behavior is identical to a fresh mount:

- **Events (§7)** are wired exactly once per node — tests assert a single
  listener, so a click fires one handler, not two.
- **Reactive text/attributes (§8, §9)** patch the *same* adopted node on signal
  change; there is no full re-render and the subscription set matches the browser
  mount.
- **`when()` (§10)** toggles its branch in place after hydration, including
  branches that were *absent* from the server HTML (e.g. a collapsed detail
  block).
- **Keyed lists (§11)** — the critical case: a list rendered `A, B, C` on the
  server, then reordered after hydration, *reuses* the existing server `<li>`
  nodes (proven by element identity), never rebuilding them. Keys ride along in
  the server markup as `data-streetui-key`.
- **Controlled inputs (§12)** adopt their server-rendered value, are two-way
  bound (typing updates the signal, signal updates the input), and carry no
  duplicate handlers.

## 6. State transfer & serialization (spec §16)

`serializeState(map)` emits an inert island —
`<script type="application/json" data-streetui-state>…</script>` — and returns
`''` for an empty map. It escapes `<`, `>`, `&`, `U+2028`, and `U+2029` as
`\uXXXX` code points, so a literal `</script>` (or a line/paragraph separator)
inside the data cannot break out of the script element. `readState(dom, root)`
parses it back through the `DOMAdapter` (never assuming a global `document`) and
returns `{}` when the island is absent or unparseable, so hydration degrades to a
cold client render rather than failing.

## 7. Router & resource SSR integration (spec §13, §14, §15)

**Router (§13, §14):** `mountRouter(router, { hydrate: true, container, shell })`
hydrates the persistent shell and the initial route in place, then takes over
client-side navigation (subsequent route changes render fresh into the outlet
while the shell persists). Dynamic `:param` and query values resolve identically
on both sides — the server renders `/docs/intro?q=hello` into markup and the
client adopts that exact markup — provided the server uses
`createMemoryHistory(path)` with the matching initial path.

**Resource (§15):** `resource()` accepts `initialData` / `initialError` /
`initialStatus`. A seeded resource starts in the corresponding non-`idle` state
and **skips the automatic initial load**, so a fetch resolved on the server is
not repeated on the client. `immediate: true` opts back into a client refetch
when that is deliberately wanted. The seed travels via the state island (§6).

## 8. Lifecycle & performance (spec §20, §27)

**Lifecycle (§20).** The synchronous server mount opens signal subscriptions via
`wireSignalBindings` / `wireReactiveList`; on the server those would live
forever. `renderToString` therefore disposes the root instance and clears
`ctx.instances` immediately after serializing — SSR has a *render* lifecycle
only, and mutating a signal after the call returns is a safe no-op (covered by a
test). The live *runtime* lifecycle is established later, on the client, by
`hydrate`, which is the sole owner of the persistent browser-side subscriptions.

**Performance (§27).** Hydration's value proposition — reusing matching DOM
instead of recreating it — is asserted directly by *element identity*: tests
capture `container.querySelector('#node')` before hydration and assert the very
same object is present afterward (and after a list reorder). This is a stronger
guarantee than a timing benchmark: it proves nodes were adopted, not rebuilt.

## 9. Constraints & dependencies (spec §17, §18, §19, §28)

**No forbidden dependencies (§28).** No React, Vue, Preact, Svelte, Solid,
ReactDOM, third-party virtual DOM, or third-party SSR/hydration framework was
added. No new packages and no new third-party runtime dependencies were
introduced at all; the only external names in the repo remain the dev/test/build
tooling (typescript, tsup, vitest, happy-dom).

**Server environment (§17).** `renderToString` runs under plain Node.js, is
framework-neutral, and drops into any Node HTTP layer (including StreetJS) — the
example's `server-entry.ts` demonstrates a clean stdout render that exits 0.

**Streaming (§18).** Streaming / progressive hydration is intentionally *not*
implemented in v0.4; it is documented as future work in
`packages/renderer/README.md`. The `ServerDOMAdapter` + `mountGraph` split leaves
room to add a streaming serializer later without a second renderer.

**Error handling (§19).** `renderToString` does not swallow errors thrown while
building the graph — they surface to the caller. In the application itself,
failures stay observable and contained through the existing `errorBoundary` DSL
block, which behaves identically after hydration.
