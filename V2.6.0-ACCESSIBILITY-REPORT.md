# StreetUI 2.6.0 — Accessibility Report

**Phase 3 of the 2.6.0 "Production Website Validation" mission.**
Subject under test: the official StreetUI website, `examples/streetui-website/`.

Scope as specified: validate accessibility across **four layers** — STRUCTURAL,
BEHAVIORAL, VISUAL, and ASSISTIVE_TECHNOLOGY — including an axe-core pass over the website
targets and a **real** Orca + AT-SPI screen-reader run. The mission is explicit: **do not
simulate assistive technology.**

## 1. STRUCTURAL — semantic graph (established at source level)

StreetUI's model is a semantic graph, so structural accessibility is largely a property of
the authored graph rather than hand-written ARIA. The website test suite
(`examples/streetui-website`, run via the public `streetui/testing` API) asserts the
structural facts that matter: landmark/section structure, heading text and order, labelled
controls and links, and per-route document metadata (title, description, canonical,
robots) via the SEO suite. These pass (58/58 website tests). This is a **source/markup**
assertion through happy-dom — it is the right thing to check in a browserless environment,
and it is *not* a substitute for a browser accessibility-tree inspection, which the
authoritative environment owns.

## 2. BEHAVIORAL — keyboard and focus (exercised in tests)

The overlay and focus machinery the website relies on (dialog/popover/tooltip/dropdown/
toast built on `portal` + `when`, plus the focus utilities) is exercised in the framework's
own happy-dom integration tests. This establishes the behavioral contract
(open/close/escape/focus-return) at the DOM-API level. Real pointer/keyboard event
dispatch in a browser, and focus-order as a user's AT would traverse it, are confirmed in
the authoritative environment.

## 3. VISUAL — axe-core — BLOCKED (sandbox)

axe-core's color-contrast and in-page rule checks require a real browser DOM and layout.
No browser exists in this sandbox (`V2.6.0-ENVIRONMENT-REPORT.md` §2), so the axe-core run
over the website's targets could not be performed here and **no axe result is reported.**

The authoritative environment owns this: `benchmarks/results/v2.5/visual-a11y.json` is an
existing real `chromium 154.0.8037.57` axe-core artifact and is the template for the v2.6
run. WCAG disclaimer carried forward: axe-core covers a *subset* of WCAG; a PASS there is
not a full WCAG 2.1 AA conformance claim.

## 4. ASSISTIVE_TECHNOLOGY — Orca + AT-SPI — BLOCKED (sandbox)

A real screen-reader validation requires Orca and the AT-SPI accessibility bus. Neither is
present in this sandbox (`orca: NONE`). Per the mission rule, this layer is **not
simulated**; it is recorded as BLOCKED and handed to the authoritative environment, where
`benchmarks/results/v2.5/accessibility-at.json` already demonstrates a real run (Orca
`/usr/bin/orca` version `46.1`, live a11y bus, pyatspi present).

## Hand-off checklist for the authoritative environment

To complete Phase 3, run in the authoritative environment and write results into
`benchmarks/results/v2.6/accessibility.json` (replacing the BLOCKED stub):

1. **VISUAL:** run axe-core over the 11 specified website targets in Chrome 154; record
   violations (expect color-contrast + rule coverage), keeping the WCAG-subset caveat.
2. **ASSISTIVE_TECHNOLOGY:** drive the served website with Orca + AT-SPI; confirm landmark
   navigation, heading jumps, accessible names on controls/links, and overlay
   announce/focus-return. Do not simulate.
3. Cross-check STRUCTURAL/BEHAVIORAL source assertions against the live accessibility tree.
