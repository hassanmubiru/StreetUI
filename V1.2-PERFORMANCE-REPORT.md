## 1. Executive summary

v1.2 keeps the entire v1.0/v1.1 architecture intact — DSL → Compiler → Semantic
Application Graph → Runtime → **direct DOM renderer**, one public `streetui`
package, StreetUI's own reactivity, **no virtual DOM, no second reactive system,
no React/Vue/Preact/Solid dependency**. It targeted the three areas v1.1
regressed: initial render, runtime bundle size, and full-list reverse.

The central, honest finding of this pass: **two of the three "regressions" were
never StreetUI algorithmic regressions — they are happy-dom measurement noise
and unavoidable DOM-engine cost, proven by CPU profiling.** Only the bundle
(+4% in v1.1) was genuinely StreetUI-attributable, and it is now flat. The pass
therefore delivered *measured allocation wins* where profiling showed StreetUI
code actually dominates (hydration, mount closures), refused speculative fast
paths where profiling showed the cost is not ours (initial render, reverse), and
added an opt-in diagnostic compiler-inspection mode — all without changing the
public API, adding a dependency, or undoing any v1.1 gain.

## 3. Initial render (§2) — profiled, no fast path claimed

CPU profile (node:inspector, 50µs) of 40 mounts of a 10k flat-text app: DSL build
3.95 ms + compile 3.25 ms + **mount 89.5 ms (92%)**. Within mount: **~50.8% GC**
(allocation pressure), **~40% happy-dom engine internals** (Node/Element/Attr/
NamedNodeMap/Text constructors, createElementNS, setAttribute — native and cheap
in a real browser, **not ours to fix**), and only **~8% StreetUI JS**.

Scenario A executes **zero v1.1-changed code** (all v1.1 changes live in list
reconciliation, never hit by a flat mount; node count is identical at 20002), so
the 104→121 "regression" was always happy-dom timing noise, as v1.1 already
disclosed. The honest StreetUI-side wins taken (all measured, op-counts identical
— createElement 10002 / createTextNode 10000 / setAttribute 10000 / appendChild
20002): (1) killed a throwaway `NodeInstance` allocated per text/form node before
the real one; (2) `applyNodeProps` now uses an allocation-free `for..in` +
`Object.hasOwn` instead of `Object.entries`; (3) early-return guards in
`wireEvents`/`wireSignalBindings` for empty events/stateRefs kill per-node iterator
and update-closure allocations. GC share moved 50.8%→50.3% and `applyNodeProps`
dropped out of the top frames — a small honest slice, because the dominant cost is
the DOM engine, not us. **cloneNode/template fast path was NOT pursued**: profiling
shows it would not touch the dominant cost and would complicate the DOMAdapter/SSR
contract.

## 4. Compiler static analysis + diagnostic inspection (§3 / §14)

New `packages/compiler/src/analysis/analyze.ts` — `analyzeGraph`: an O(n) post-order
pass classifying each node `{isStatic, isStaticSubtree, hasDynamicText,
hasDynamicAttr, hasEvents, isList, isConditional}` with roll-up (a dynamic
descendant taints ancestors) plus summary counts — and `inspect.ts`
(`inspectCompilation` → per-node classification + hydration hint
`adopt-static | verify-dynamic` + `staticRatio`; `formatInspection` → text report).

**Critical discipline:** analysis is **NOT** wired into `compile()`. Running it
eagerly would add O(n) Map+record allocation to every compile and re-regress the
very initial render this pass targets. It is opt-in, diagnostic-only, and
tree-shakeable: exported from a dedicated `@streetui/compiler/diagnostics` subpath
and re-exposed **only** through the dev-facing `streetui/testing` subpath — never
on the runtime `streetui` barrel. Two integration tests assert both that all three
symbols resolve from `streetui/testing` and that none appear on `streetui`.
(Compiler's inspection type was renamed `InspectedCompilationNode` to avoid
colliding with devtools' frozen `InspectedNode`.)

## 5. Reverse-list (§9) — profiled, fast path refused (honest)

CPU profile of one 10k reverse (wall ~344 ms): **~98% is happy-dom DOM-engine
internals** (child-list splice + sibling-pointer updates in insertBefore, plus
happy-dom internally detaching the connected node from its old slot per spec).
**StreetUI reconciler JS is <2%.** A counting adapter over one reverse:
createElement 0 / createTextNode 0 / removeChild 0 / **insertBefore 9999**. The
keyed-identity short-circuit holds perfectly, and 9999 = n − |LIS| = 10000 − 1 is
the **mathematical minimum** number of moves to reverse 10k keyed nodes (LIS of a
strictly-decreasing permutation is 1). A "reverse fast path" cannot reduce moves
below n−1, so it would add bundle + branch complexity + keyed-identity risk for
**zero** measured DOM benefit. Not pursued. The nextSibling guard in
`reorderDomMinimal` was deliberately **not** weakened — it saves work on the small
permutations that produced v1.1's append/prepend/reorder wins.

## 6. Runtime bundle (§6 / §7) — flat, tree-shaking verified

The one genuine v1.1 regression (gzip 27488→28680, +4%, from the list-plan + LIS
machinery) is now **flat**. Work done: (1) the new diagnostics were first
accidentally pulled into the runtime barrel via `export *`, inflating gzip to
29744; moving them to the `@streetui/compiler/diagnostics` subpath and off the
compiler main index brought the runtime barrel back to baseline. (2) All 19
packages carry `sideEffects:false`; tree-shaking verified via esbuild
bundle+minify+treeshake: a minimal `import {signal}` app = **2662 B gzip**, a
typical app (signal+streetui+compile+createRenderer) = **10526 B gzip**,
full-barrel minified = **19855 B gzip**. The 28.7 KB scenario-H figure is a
worst-case *unminified full-barrel dev-readable* artifact (kept unminified for
apples-to-apples with the v1.0/v1.1 baselines); real apps pay 2.6–10.5 KB.

**Net vs v1.1: +84 B (+0.29%) — disclosed, not hidden.** A/B attribution:
hydrate.ts guards + lazy diag string +47 B, mount.ts closure guards +19 B, mount
restructure +18 B. This +84 B buys the real hydration allocation win below and a
mount closure reduction that likely helps *more* in a real browser (native DOM
constructors are cheap there, so JS/GC is a larger relative share). It is ~7% of
v1.1's own +1192 B and undoes no v1.1 gain. No minification of the shipped artifact
was done to manufacture a smaller number.

## 7. Hydration (§11 / §12) — allocation wins, metadata refused

Unlike mount and reverse, **pure hydration IS StreetUI-JS-dominated** (profiled
with containers pre-built outside the measured region so happy-dom's innerHTML
parser is excluded): hydrateNode ~55% + hydrateChildren ~14% + GC ~23%; happy-dom
accessors only ~6%; wall ~3.8 ms/10k. Two provably-wasted allocations removed in
`hydrate.ts`: (1) the per-child diagnostic path string is now built only when a
diagnostics sink is attached; (2) the per-type update closure
(text/heading/input/button) is built only for genuinely-reactive nodes
(`graphNode.stateRefs.length !== 0`). **Measured: profiled samples 786→489 (−38%),
wall ~3.8→~3.3 ms, G_created=0 preserved** (counting-adapter verified). The same
closure guard was applied to `mount.ts`.

**§12 compiler-guided hydration metadata was NOT pursued (honest decision):** the
dominant hydration cost is unavoidable NodeInstance + instance-map creation (the
live runtime needs the instance index for later targeted updates) plus GC — not
the tag re-verification that `staticSubtree` metadata could skip — and skipping
verification would weaken hydration-mismatch tolerance, which §11 forbids.

## 8. Keyed lists, fine-grained reactivity & memory (§10 / §13)

All v1.1 keyed-list wins and invariants are intact and re-measured: append/remove
create/remove exactly the minimal DOM nodes (append 3 created; remove 1 removed),
reorder/reverse/update create and remove **zero** nodes, and `data-streetui-key`
identity + targeted per-item updates + cleanup are unchanged. Fine-grained
invariants hold: single-signal update = **1** DOM mutation; deep-state update
touches **1** node; SSR output is **byte-identical at 338920 bytes**.

Memory stress (§13) extended with two hydration-cycle tests: 40 hydrate/unmount
cycles drain `ctx.instances` to 0 and leave the container node-count unchanged; 25
reactive-text cycles prove post-hydration signal writes still reach adopted nodes
(the v1.2 stateRefs-guarded closure path still wires live bindings) and
post-unmount writes are safe no-ops. The existing 300-op keyed-list mutation-stress
returns to baseline. Renderer suite 133→135; the guards demonstrably did not break
cleanup (reactive nodes still subscribe/track/unsubscribe; static nodes never
subscribed, so there is nothing to leak).

## 11. Known limitations

1. All timings are **happy-dom / Node**, not a real browser — absolute ms is
   high-variance (A p95 is ~2× its min on identical code). Only invariant counts
   and same-run relative deltas should be trusted. Real-browser numbers remain
   BLOCKED.
2. **No competitor comparison exists** — offline registry + no browser. Any
   "faster than X" reading is unsupported and intentionally absent.
3. The scenario-H bundle figure (28764 B) is a deliberately **unminified
   full-barrel** artifact for baseline parity; production apps ship 2.6–10.5 KB
   gzip (measured), not 28.7 KB.
4. Two of the three v1.2 targets (initial render, reverse) were proven by profiling
   to be non-StreetUI cost (happy-dom engine + measurement noise); the honest
   deliverable there is the profiling evidence and the *refusal* to add speculative
   complexity, not a headline speedup.
