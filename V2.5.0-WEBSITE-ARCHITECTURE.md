# StreetUI 2.5.0 — Official Website Architecture

**Deliverable:** `examples/streetui-website/` — the official StreetUI website, built
entirely with StreetUI as a production dogfooding application.

**Status in this (sandbox) environment:** source typechecks (`tsc --noEmit` → exit 0),
18-section content layer + 13 routes build their real semantic graph, 13/13 tests pass
via the public `streetui` / `streetui/testing` API, the three entry bundles compile, and
the bundled `server-entry.js` renders real SSR HTML. Browser render, Lighthouse/perf, and
assistive-technology validation are deferred to the authoritative environment (see the
execution-boundary note at the end).

---

## 1. Design principle: the website *is* a StreetUI application

The site is not a demo of StreetUI output pasted into a static page. Every node the
browser sees is produced by the same pipeline the framework ships:

```
Semantic TS DSL  →  compile()  →  Semantic Application Graph  →  Runtime  →  Direct DOM Renderer
```

There is no second renderer, no virtual DOM, no React/Vue/Svelte/Solid runtime, and no
hand-written HTML template for page content. `index.html` contains only an empty
`<div id="app">` and a `<script type="module">` that boots the bundled client entry.
All structure, navigation, theming, search, the playground, and the server render go
through the public `streetui` package exactly as an external consumer would import it.

Public install surface is unchanged: a consumer runs `npm install streetui` and imports
from `streetui`, `streetui/server`, and `streetui/testing`. The example's `package.json`
depends on `streetui: workspace:*` — the same single public package, not internal
`@streetui/*` subpackages.

Separating `content.ts` (data) from `routes.ts` (render) means a single
`/docs/:section` route renders all 18 documentation sections, and the search index is a
`derived` projection over that same data rather than a hand-maintained duplicate.

## 3. Routing architecture

`createRouter({ routes, history, notFound })` with 13 routes:

`/` (home, exact-active) · `/getting-started` · `/docs` · `/docs/:section` ·
`/api` · `/examples` · `/playground` · `/benchmarks` · `/changelog` · `/blog` ·
`/blog/:slug` · `/about` · `*` (404 fallback).

Features exercised:

- **Dynamic params** — `/docs/:section` and `/blog/:slug` read `ctx.params`.
- **Query params** — `/examples` seeds its filter from `ctx.query.get('q')`
  (`ctx.query` is a `URLSearchParams`, not a record).
- **Active-link state** — `router.isActive(href, { exact })` returns a
  `ReadonlySignal<boolean>`; `navLink` mounts an `(active)` marker through `when(...)`
  with no manual class toggling. `Home` uses `exact: true` so it is not active on `/docs`.
- **Fallback** — unknown paths resolve to the 404 route; `currentRoute.get().isFallback`
  is `true`.
- **Persistent shell** — `mountRouter(router, { container, outletId: 'page-outlet',
  shell, hydrate })` renders the shell once; only the outlet subtree changes on navigation.

## 4. Persistent shell

`websiteShell(page, ctx)` renders, in order: a skip link (`#skip-link` → `#page-outlet`),
the `#site-nav` landmark (brand `h1`, primary nav links, external GitHub link, theme
toggle, docs search), the router outlet, and the `#site-footer`.

The shell is **dual-purpose** for SSR vs. runtime without duplicating the definition.
`routerOutlet(scope, id)` emits `container('router-outlet', …, { id })`. On the client the
router populates that outlet; on the server `ShellContext.renderOutlet` fills it inline,
emitting a node with the **same key (`'router-outlet'`) and id (`'page-outlet'`)** so that
client hydration adopts the server node identity rather than recreating it.

## 5. Reactive theme system (SSR/hydration-safe)

`createTheme({ storage?, root?, initial? })` returns a controller whose `choice` is a
`signal<'light'|'dark'|'system'>`, and whose `resolved` and `label` are `derived`
(`ReadonlySignal` — not writable). It applies `data-theme` to `document.documentElement`
through an `effect`.

SSR-safety is structural, not conditional-at-call-site: `localStorage`, `matchMedia`, and
`document` access are each isolated behind guards, so the identical module runs during SSR
(no DOM, no storage) without throwing and falls back to in-memory storage. The server
renders with the default theme and the client applies the persisted/system choice on
mount. Because `data-theme` lives on `<html>` — outside the hydrated `#app` container —
this is a legitimate post-hydration update, not a hydration mismatch.

`cycle()` advances `light → dark → system → light`; the default when nothing is stored is
`system`.

## 6. Docs search

`createSearchState(querySignal)` returns `{ query, results }` where `results` is
`derived(() => searchContent(query.get()))` — a live substring search over the derived
`SEARCH_INDEX` (titles + kinds across docs, API, examples, blog), capped at 10 results.
The shell binds the search `<input type="search">` to `query` and renders results through
`listOf(...)`; a `when(...)` guard shows a `#search-empty` state when a non-empty query
matches nothing.

## 7. Playground (built in StreetUI)

`buildPlayground(content, state)` is a real StreetUI UI, not an embedded iframe or a React
widget: a demo selector (`counter` / `list` / `greeter`), a counter with
increment/decrement/reset bound to a `signal`, a keyed `listOf` list with add/remove, and
a greeter with a bound input driving a `derived` greeting. Tests drive it through real
events: `trigger(findByRole(container, 'button', { name: 'Increment' }), 'click')`.

## 8. SSR / hydration

`renderWebsite(path)` builds a memory-history router, resolves the current route, composes
one app page via `websiteShell(page, { router, theme, search, renderOutlet })`, and returns
`renderToString(compile(app))` plus a `serializeState({ [STATE_KEY]: { path, themeChoice }})`
script. The theme choice is captured **before** `theme.dispose()` / `router.destroy()`.

The bundled `server-entry.js` was executed in-sandbox against the real `streetui` package
and produced a 2,557-byte HTML document containing `id="page-outlet"`, `id="brand"`, the
route content (`Reactivity`), and the embedded state script — end-to-end proof at the Node
layer. The hydration test mounts, snapshots `container.innerHTML` as "server HTML",
re-mounts with `{ hydrate: true }`, asserts the `#brand` node identity is preserved, and
confirms live client navigation after hydration.

## 9. Build

The example's configured bundler (`tsup`) cannot run in this sandbox: it writes a temp
`tsup.config.bundled_*.mjs` and then `unlink`s it, but the mounted workspace forbids
`unlink` (`EPERM`). This is the documented mnt-unlink limitation, not a code defect. The
three entries (`index`, `browser-entry`, `server-entry`) were instead bundled directly
with the repo's esbuild (ESM, `platform: neutral`, `streetui*` externalized) — all three
compile cleanly (index 38.5 kB, browser-entry 37.2 kB, server-entry 37.1 kB) and the
output runs. In the authoritative environment `tsup` runs normally.

## Execution boundary

Browser rendering, Core Web Vitals / performance measurement, and assistive-technology
(screen-reader) validation are **not** run here. The sandbox has no Chrome/Firefox, no
Orca/AT-SPI, and no reachable npm registry. Those runs belong to the authoritative
environment (Chrome 154 / Firefox 155 / Orca+AT-SPI) and are tracked in
`V2.5.0-PERFORMANCE-REPORT.md` and `V2.5.0-ACCESSIBILITY-REPORT.md`. No browser, perf, or
AT numbers are reported here, and none are simulated.
