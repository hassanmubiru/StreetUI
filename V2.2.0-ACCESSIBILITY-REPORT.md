# StreetUI 2.2.0 — Accessibility Report (Phase 2)

**Date:** 2026-09-29
**Scope:** the accessibility validation milestone.
**Overriding rule:** **Do NOT claim screen-reader conformance unless an actual
assistive technology is executed.** No AT is available in this headless VM, so
assistive-technology conformance is **BLOCKED** and reported as such. What *is*
verified is verified through the public API only, and its limits are stated
plainly.

---

## 1. What was built

A single consolidated accessibility regression **gate** lives at
`packages/testing/src/a11y-regression.test.ts`. It exercises StreetUI's
accessibility behaviour using **only the public API** — `@streetui/*` public
exports plus the `streetui/testing` helpers (`render`, `findByRole`,
`openOverlay`, `pressKey`, `renderServerThenHydrate`). It imports no internal
deep paths, so it is a genuine consumer-level check.

**16 accessibility tests** were added. With them the `@streetui/testing` package
now runs **50 tests** (was 34). The suite runs under happy-dom, which is a real
DOM implementation — so DOM structure, ARIA attributes, roles, ids, and keyboard
event dispatch are exercised against a real node tree.

## 2. What the 16 tests cover

- **Deterministic `a11yId` generation** — stable, collision-free ids across renders.
- **ARIA state synchronization** — booleans serialize as the strings `"true"` /
  `"false"`; `disabled` is emitted as a boolean attribute, not a string.
- **Overlay semantics** for dialog, popover, dropdown, tooltip, and toast
  (correct `role`, `aria-modal`, labelling relationships).
- **Focus management** — `Tab` / `Shift+Tab` focus trapping inside a modal,
  `Escape` to close, arrow / `Home` / `End` navigation plus `Enter` activation.
- **Focus restoration** — focus returns to the invoker after an overlay closes.
- **Nested-modal ownership** — the innermost overlay owns focus; unwinding restores
  the correct parent.
- **Live regions** — `createAnnouncer` produces the expected `aria-live` regions.
- **SSR → hydrate a11y preservation** — accessibility attributes present in the
  server markup survive hydration unchanged (`renderServerThenHydrate`).

## 3. What is verified vs. what is BLOCKED

**Verified (deterministic, in-environment):** the *static and behavioural*
accessibility contract — that the framework emits the correct roles, ARIA states,
ids, live regions, and that keyboard interaction and focus management behave as
specified, including across SSR→hydration. This is a real regression gate that
will catch a future change that drops or corrupts these attributes.

**BLOCKED — and explicitly not claimed:**

| Capability | Status | Why |
|------------|--------|-----|
| Screen-reader / AT announcement | **BLOCKED** | No NVDA / JAWS / VoiceOver / Orca, no AT-SPI bus, and no browser to host one in this headless Node VM. Actual assistive-technology output cannot be observed, so it is not claimed. |
| Browser focus-visibility (`:focus-visible` rendering) | **BLOCKED** | Requires a real browser; none is present. |
| Colour-contrast conformance | **BLOCKED** | Requires rendered pixels in a real browser. |

These limits are documented **inside the suite itself**, not only here, so the
gate can never be mistaken for an AT-conformance pass. Static ARIA/role/state
derivation being correct is necessary for accessibility but is **not** the same as
a screen reader announcing correctly, and it is not reported as one.

## 4. What remains for 2.3

Run the accessibility suite through an actual assistive technology (a real screen
reader driving a real browser) to convert the AT gate from BLOCKED to a measured
pass, and add colour-contrast and `:focus-visible` checks once a browser is
available.

---

*Note: this is a sensitive area only in the sense that accessibility claims carry
real weight for real users — which is exactly why the unverified AT capabilities
are held at BLOCKED rather than asserted.*
