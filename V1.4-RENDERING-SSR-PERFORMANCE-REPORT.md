## 4. SSR profiling & optimization (§12–§15)

**Where the time goes** (renderToString of /users, 10k rows, ServerDOMAdapter):

| Phase | Median | Share |
|---|---|---|
| Mount (build the ServerDOM tree) | 116.2 ms | **62.1 %** |
| Serialize (tree → HTML string) | 61.2 ms | 32.7 % |
| Text escaping (subset of serialize) | — | ~3.8 % |

SSR is **mount-dominated**, not escape-bound. The mount phase is the shared renderer and
was deliberately left untouched (no rewrite). Optimization targeted the serialize phase's
allocation behaviour only.

**What shipped (byte-identical, no API change):**

1. Single-scan fast-path `escapeHtmlText` / `escapeHtmlAttr` with an early return when no
   special character is present (skips 3 regex allocations in the overwhelmingly common
   no-`&<>"` case).
2. Hoisted `SERIALIZED_PROPERTY_ENTRIES` to module scope (was allocating ~80k throwaway
   `Object.entries` arrays per /users render).

**Measured effect — deterministic same-process A/B** (one /users tree, shipped serializer
vs a pre-v1.4 replica, same run):

| | Median serialize |
|---|---|
| Pre-v1.4 replica | 103.9 ms |
| Shipped v1.4 | 64.1 ms |
| **Speedup** | **1.62×**, output **byte-identical** |

Per-node escape microbench (the real call pattern — 70,021 runs, 0 with special chars):
7.19 ms → 1.49 ms, byte-identical.

> **Measurement caveat:** end-to-end `renderToString` cross-run medians bounce 184–233 ms in
> this 2-core VM, too noisy to quote a percentage. The SSR win is reported only as the
> deterministic same-process serialize A/B. A naive whole-body escape microbench *misleads*
> (it makes the fast path look slower, because V8's regex `.replace` is fast on one 3.6 MB
> string) — the serializer calls escape once per text node, not once per body, so escaping
> is benchmarked per-node.

**Byte-identity gate (SSR contract preserved):** all five route bodies sha256-identical
before/after — overview `19d86cbbf7a0c17a`, dashboard `4f6b4a396fab708d`, users
`f8f20c0db090936c`, controls `3616bce91f0fd354`, settings `42127b6fc814828e`. Hydration
still creates 0 nodes.

## 5. Bundle, server/client boundary & tree-shaking (§17–§19)

**Finding:** the server serializer chain (`ServerDOMAdapter` → `serializeServerNode` →
`escapeHtmlText`/`escapeHtmlAttr`/`VOID_ELEMENTS`) was leaking into **client** bundles that
never import SSR — even a bare `import { signal } from 'streetui'`. Root cause: the
top-level convenience singletons `export const serverDOMAdapter = new ServerDOMAdapter()`
and `browserDOMAdapter = new BrowserDOMAdapter()` were not annotated, so esbuild treated the
bare `new X()` as an import-time side effect and retained the classes (and their serialize
methods) everywhere. This was **pre-existing** (present in v1.3) and was enlarged ~100 B by
the §13/§14 escape code.

**Fix:** annotate both singleton instantiations `/* @__PURE__ */ new X()` (in
`packages/dom/src/{server-adapter,browser-adapter}.ts`). The exports remain — the frozen API
is untouched; only the unused initializers become droppable, letting the server serializer
tree-shake out of non-SSR client bundles.

**Measured (esbuild bundle+minify+treeShaking, gzip):**

| Profile | v1.3 gzip | v1.4 gzip | Δ |
|---|---|---|---|
| minimal (reactivity + client render) | 8606 | **7619** | **−987 (−11.5 %)** |
| typical (SPA: router/forms/i18n/store/resource) | 15365 | **14377** | **−988 (−6.4 %)** |
| realApp (built demo entry) | 15690 | **14667** | **−1023 (−6.5 %)** |
| full (`import *`, retains SSR) | 20105 | **20205** | **+100 (+0.5 %)** |

The `full` profile imports everything, so it legitimately retains SSR via `renderToString`
and carries the §13/§14 serializer code — its +100 B is disclosed and expected. Client
profiles that don't use SSR now **shrink ~1 KB gzip**. Verified: a `signal`-only bundle no
longer contains `&quot;`/`&amp;`/the VOID tag list/`<!--` serializer strings.

The framework ships **no CSS**. esbuild is a measurement-only tool, not a runtime dependency.

## 9. Measured strengths (this environment)

- SSR serialize phase **1.62× faster**, byte-for-byte identical output.
- Client bundles **~1 KB gzip smaller** (minimal −11.5 %) after closing the serializer leak.
- Hydration creates **0** DOM nodes; fine-grained update touches exactly the nodes that
  changed (2 writes, independent of list size); clean unmount with 0 orphans.

## 10. Measured weaknesses (this environment)

- SSR is **mount-dominated (62 %)**; the remaining headroom is in the shared renderer, which
  v1.4 deliberately did not rewrite — so SSR throughput gains beyond the serialize phase are
  out of scope here.
- The `full` (`import *`) bundle grew +100 B gzip; unavoidable when SSR is actually imported.
- No real-browser or competitor evidence is available in this environment.
