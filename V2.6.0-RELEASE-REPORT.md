# StreetUI 2.6.0 — Release Report

**Phase 10 of the 2.6.0 "Production Website Validation & Evidence-Driven Fixes" mission.**
Continues published 2.5.0. This report consolidates the Phase 8 framework regression gate,
states what 2.6 changed, and records the release decision.

The mission's defining constraint held throughout: **no feature expansion, no size growth
for its own sake, no architecture change, no second renderer or reactive system, single
public `streetui` package** (entries `.`, `/server`, `/testing`). The pipeline is
unchanged: Semantic TS DSL → Compiler → Semantic Application Graph → Runtime → Direct DOM
Renderer.

---

## 1. What 2.6 changed — and did not

**2.6 changed no framework runtime or public-API code.** It is a validation mission. The
only code touched was the **example website** and **documentation/report** content:

- Website SEO/metadata layer added (`examples/streetui-website/src/metadata.ts`,
  `shell.ts`, `components.ts`) using the existing first-class `head()` primitive shipped
  in 2.0 — one complete head layer per route (finding **F-7**, see
  `V2.6.0-FRAMEWORK-FINDINGS.md`). Zero framework change.
- One prose correction in the website content (`content.ts`): the Hydration section no
  longer implies a non-existent bare `hydrate()` export (see
  `V2.6.0-CONTENT-AUDIT-REPORT.md`).
- Website regression + SEO test suites expanded (58/58).
- The 2.5 findings F-1..F-6 were addressed in Phase 4 **additively** (docs, type exports,
  the exported `ROUTER_OUTLET_KEY` constant, the application-level `code`/preformatted
  solution) — no new runtime primitive, no second renderer, no package split.

Because the published `streetui` package's runtime and surface did not change, the
version-pinning tests still assert **2.5.0**, and they pass.

## 4. Clean-room packed-artifact execution (sandbox-valid substitute for offline install)

Because registry-backed install is blocked, the packed tarball was extracted and executed
in a clean `/tmp` directory, which exercises the real published file layout without a
package manager:

- **ESM:** `import` of `dist/index.js` + `dist/server.js` → `VERSION === '2.5.0'`,
  188 named exports, `renderToString` produced 103 bytes for the probe app.
- **CJS:** `require` of `dist/index.cjs` + `dist/server.cjs` → `VERSION === '2.5.0'`,
  `renderToString` produced 60 bytes.

The framework import/require path does not touch esbuild; the esbuild dependency only
backs the bundled CLI bin, which is why the offline `npm install` limitation does not
impede the framework itself.

## 5. Framework findings disposition (Phase 9)

Phase 9 asks whether any **minimal framework change** is warranted. Per the 6-point
justification in `V2.6.0-FRAMEWORK-FINDINGS.md`:

- **F-1..F-6** (from 2.5): addressed additively in Phase 4; none required a runtime
  primitive, a second renderer, or a package split.
- **F-7** (head managers scoped per render context; two layers do not merge under
  `mountRouter`): classified **documentation / ergonomics, not a defect**. A cross-context
  head merge would be new machinery (prohibited feature expansion) and would risk the
  byte-identical SSR invariants. **Decision: no framework change in 2.6.** The website-level
  one-complete-layer-per-route design fully resolves it; the follow-up is a routing/
  metadata docs note (in-repo guidance already present).

**Phase 9 outcome: no framework code change is warranted. Confirmed, not merely deferred.**

## 6. Release decision

**Decision (sandbox portion): HOLD the published framework version at 2.5.0. Do not bump
to 2.6.0 from the sandbox, and do not publish from the sandbox.**

Rationale:

1. **No framework code changed in 2.6.** All work was website-level or documentation. The
   published `streetui` package's runtime, API surface (188 exports), and SSR output
   (byte-identical to the v1.6 golden) are unchanged. There is no code delta that a
   framework version bump would describe.
2. **The release-grade validation gates a bump would rest on are BLOCKED here.**
   Browser-measured website performance and real Orca+AT-SPI accessibility — the headline
   deliverables of this mission — are owned by the authoritative environment and were not
   measured in the sandbox. Bumping/publishing on sandbox-only evidence would violate the
   evidence-integrity rule.
3. **The version-pinning tests assert 2.5.0 and pass.** Holding keeps the suite honest and
   green.

**Hand-off to the authoritative environment.** Whether to tag a **2.6.0 validation
milestone** is that environment's call, to be made only after it runs the browser
performance suite (Chrome 154 / FF 155), the axe-core VISUAL pass, and the real Orca+AT-SPI
ASSISTIVE_TECHNOLOGY run, and populates
`benchmarks/results/v2.6/{website-performance,accessibility}.json` with real numbers. If it
elects to bump, the coordinated change is the established one: `version.ts` `VERSION`, the
CLI version, the two stability assertions (`streetui.public.test.ts`,
`public-api.stability.test.ts`), the 18 package.json versions, and the manifest — plus the
deferred CHANGELOG entries (see §7). This report does not pre-empt that decision and claims
no published 2.6.0.
