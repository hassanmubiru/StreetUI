# StreetUI v0.9 — Ecosystem & Developer Experience

*Verified in the `/work` build copy. Nothing below is fabricated: browser and
registry remain unavailable and are reported as limitations, not simulated.*

## 1. Executive Summary

v0.9 makes an existing StreetUI application easier to build, debug, inspect,
test, understand, and release — without adding framework surface area. It is a
purely additive developer-experience layer: a first real (headless) DevTools
surface composed from the one semantic graph and the app's own reactive objects;
sharper testing helpers built on the real renderer; optional, privacy-safe
diagnostic and observability boundaries; a non-mutating release-readiness check
with a machine-readable manifest; and a documentation portal covering only real
APIs. No new renderer, reactive system, router, vdom, JSX, component library,
streaming SSR, or hosted telemetry was introduced. Every one of the 529 v0.8
tests is retained; the suite now stands at 571.

## 2. Baseline (starting state)

Starting from the completed and verified v0.8 milestone: 18 packages
(`core, state, graph, dsl, compiler, runtime, events, scheduler, dom, renderer,
router, forms, i18n, context, cli, devtools, testing`, plus private
`benchmarks`). v0.8 verified counts: build 27, typecheck 42, tests 529. Existing
inspection primitives `inspectApplication(compiled)` and
`diagnosePerformance(compiled)` were already present and became the foundation
for the DevTools surface rather than being replaced.

## 3. DevTools

`@streetui/devtools` now exposes `createDevTools(compiled, sources?, options?)`,
returning a headless `DevToolsSession { snapshot, refresh(), selectNode(id),
format() }`. It is a data-and-panels layer: any host (browser panel, CLI, test)
renders the snapshot. Nothing in the runtime or the CLI imports it, so a session
exists only when dev code opts in and production pays no cost. `refresh()` is the
only way values change (explicit-refresh protocol); `selectNode(id)` returns a
subtree from the captured graph to back a UI tree inspector. Panels:
application, graph, signals, performance (always), and router/resources/forms/
contexts/i18n (only when that live source is registered). Delivered with 11 new
panel tests.

## 4. Inspection Architecture

Inspection data is strictly separated from any UI. All inspectors are one-shot
reads (`peek`) of the single `CompiledApplication` graph plus the app's live
reactive objects — there is no second graph and no second reactive system, and
no inspector ever mutates or subscribes. The compiled graph knows signal *ids*,
not live instances, so the application registers whichever reactive surfaces it
wants visible via `DevToolsSources`. This keeps DevTools decoupled (structural
interfaces for router/forms/context/i18n, no extra dependencies) and keeps the
runtime unaware of DevTools entirely.

## 5. Signals

`inspectSignal(signal, options?)` reports `kind` (`writable` vs `derived`),
`value`, and `observerCount`, using the public `signalKind()`/`observerCount()`
API in `@streetui/state` — no private fields are read. Values can be redacted
via `{ redact: true }` or a mapping function, and the DevTools session can redact
all registered signals at once (`redactSignals`) for shared or recorded sessions.
The signals panel also lists `boundSignalIds` (distinct ids referenced anywhere
in the graph).

## 6. Router

`inspectRouter(router)` snapshots the current route's `path`, `pattern`,
`params`, `query`, and `isFallback` from the router's `currentRoute` signal. It
is inspection-only — navigation is never triggered from DevTools — and is
described by a structural `RouterLike` interface so devtools does not depend on
`@streetui/router`.

## 7. Resources

`inspectResource(resource, options?)` reports `status`, `loading`,
`isRefetching`, `hasData`, `hasError`, and the error's constructor name
(`errorName`). The loaded `data` and error `errorMessage` are omitted unless the
caller passes `{ includeData: true }`, because a resource payload commonly
carries user or secret data. This is the sensitive-by-default posture required by
§16/RULE 18.

## 8. Forms

`inspectForm(form, options?)` reports `fields`, per-field validation `errors`,
`touched`, `dirty`, `valid`, and `status`. Entered field `values` are omitted
unless the caller passes `{ includeValues: true }`, so passwords and other secret
inputs never reach a panel by default.

## 9. Hydration Diagnostics

`@streetui/renderer` gained dev-only, opt-in hydration diagnostics. Hydration
remains self-repairing and local: on a mismatch the renderer mounts a fresh
subtree in place and drops the offending element, and never throws globally. A
`HydrationDiagnosticSink` can *observe* those repairs, reporting mismatch `type`
(`tag-mismatch`/`missing-element`/`surplus-element`), `expected`, `found`,
`path`, `nodeId`/`nodeType`, recovery `action`, and a one-line `message`.
Helpers `createHydrationDiagnosticCollector()` and
`consoleHydrationDiagnosticSink()` are provided. With no sink attached there is
zero extra work on the hydration path.

## 10. Testing Improvements

`@streetui/testing` renders through the real renderer into a real
(happy-dom/jsdom) DOM. `render(app)` returns a `RenderResult` with container and
tag/text/selector queries; `renderOnce(app, fn)` auto-cleans up. Higher-level
helpers: `findByText`, `findByRole`/`findAllByRole` (explicit then implicit ARIA
role, optional accessible-name filter), `flushUpdates` (flush → microtask →
flush), and `waitFor` (poll with flushing until truthy). `renderServerThenHydrate`
provides a first-class SSR→HTML→hydrate→assert workflow with optional mismatch
collection. No private-graph access, no Jest/Vitest clone. Note: the spec's
candidate name `renderTestApp` was **not** added — the real, existing equivalents
are `render`/`renderServerThenHydrate`, and the docs reflect the real names.

## 11. Browser Validation

No browser is available in this environment. Per RULE 2, no browser results are
fabricated. The testing helpers are browser-ready — they run against the real
renderer through `BrowserDOMAdapter` and are exercised here under happy-dom/jsdom
— but assertions that require an actual browser (real layout, real event
dispatch in a live page) were **not** run and are not claimed. The harness is in
place for whenever a browser becomes available.

## 12. Registry Validation

No package registry is reachable. Per RULE 3/RULE 4, no registry publish or
registry-install verification is claimed. What *is* verified is the offline
tarball consumer gate (below): packages are packed and installed from tarballs
with no workspace linking. `npm publish` was not run and is not asserted to have
succeeded.

## 13. Release Tooling

`scripts/release-check.mjs` is a non-mutating release-readiness gate over the 17
public packages. It checks publish metadata (license MIT, `sideEffects:false`,
`publishConfig.access:"public"`, a `files` whitelist, dual-module `exports` with
per-condition types), internal `@streetui/*` dependency resolution, concrete
range satisfiability, cross-package version alignment, and `dist/` presence. It
edits nothing, publishes nothing, and emits a machine-readable manifest
(`dist-tarballs/release-manifest.json`). Exit is non-zero only on an error-level
finding. Current run: **RELEASE CHECK OK, 1 warning** — the public packages
honestly span four versions (0.1.0/0.2.0/0.5.0/0.6.0), surfaced as a warning for
a release owner to resolve intentionally rather than papered over. Root scripts
`release:check/meta/pack/smoke` and `readmes` were wired up.

## 14. Documentation

A documentation portal was added under `docs/`: `README.md` (index),
`architecture.md` (DSL→compiler→graph→runtime→renderer pipeline, reactivity,
lifecycle, SSR/hydration, router, resources, CLI), `devtools.md`, `testing.md`,
`observability.md`, and `integration.md` (DOM / HTTP-resource / routing / forms /
i18n / logging / testing / CLI boundaries). Every documented API was read from
source first; no planned or non-existent API (e.g. `renderTestApp`) is documented
as if it exists.

## 15. Security / Privacy

Sensitive data is off by default everywhere: resource payloads and form values
are hidden unless explicitly requested, signal values can be redacted, context
values are never dumped, and diagnostic contexts carry only non-sensitive
identifiers (package/operation/node/route/resource) — never tokens, secrets,
cookies, or entered values. Framework error messages carry structured context
but never a stack or environment values; production stack-disclosure stays with
the server layer. No observability path sends anything over the network.

## 16. Public API Changes

All additive. New in `@streetui/devtools`: `createDevTools`, `DevToolsSession`,
`DevToolsSources`, `DevToolsOptions`, the panel/snapshot types, and the reactive
inspectors `inspectSignal`/`inspectResource`/`inspectRouter`/`inspectForm`/
`inspectContext`/`inspectI18n` with their inspection/option types. New in
`@streetui/core`: `DiagnosticSink`, `DiagnosticContext`, `frameworkError`/
`StreetFrameworkError`, `reportDiagnostic`, `consoleDiagnosticSink`,
`formatDiagnosticContext`. New in `@streetui/scheduler`: `SchedulerDiagnostics`
and `Scheduler.setDiagnostics`. New in `@streetui/renderer`:
`HydrationDiagnostic(Sink)`, `createHydrationDiagnosticCollector`,
`consoleHydrationDiagnosticSink`. New in `@streetui/testing`: `findByText`,
`findByRole`/`findAllByRole`, `flushUpdates`, `waitFor`, `renderServerThenHydrate`.
No existing signature was changed or removed.

## 17. Dependencies

No new third-party runtime dependencies were introduced. `@streetui/devtools`
inspects router/forms/context/i18n through local structural interfaces rather
than importing those packages, and remains absent from the runtime and CLI
dependency graphs (verified: nothing outside `packages/devtools` and the examples
imports `@streetui/devtools`; `packages/cli/package.json` does not depend on it).
`@streetui/scheduler` stays dependency-free — `SchedulerDiagnostics` is a local
structural type.

## 18. Tests (exact count)

**571 tests pass, 0 fail** (up from the protected 529 baseline; +42 net new).
No v0.8 test was deleted, skipped, weakened, or marked `.only`/`.skip`. New
coverage includes DevTools panels (11), reactive inspectors (10), observability
(6), scheduler diagnostics (+2), testing helpers (9), and hydration diagnostics
(18). The lone stderr line in the run is the *name* of the passing
"isolates job failures" scheduler test, which deliberately throws inside an
isolated job — not a failure.

## 20. Typecheck

## 21. Package Validation

`scripts/pack-tarballs.mjs` produced **17 tarballs**. `scripts/consumer-smoke.mjs`
created a throwaway consumer project, installed **16 `@streetui/*` packages from
tarballs offline with no workspace linking**, and ran both an ESM and a CJS
consumer that server-rendered successfully (`ESM-SSR-OK`, `CJS-SSR-OK`). The v0.8
offline packaging gate therefore still holds under v0.9.

## 22. Known Limitations

No real browser and no reachable package registry in this environment; real-page
browser assertions and registry publish/install are not performed and not
claimed (RULE 2/3/4). The public packages span four versions — intentional to
report, still to be aligned before a coordinated release. DevTools is a headless
data layer; a graphical panel UI consuming these snapshots is left to a host and
is out of this milestone's scope.

## 23. Deferred Work

A graphical DevTools panel application; version alignment + a coordinated
publish once a registry is reachable; live in-browser validation of the testing
harness; and optional deeper wiring of DevTools/testing into more of the example
apps. None of these are blockers for the v0.9 DX layer.

   the existing `inspectApplication`/`diagnosePerformance`; no subsystem was
   re-architected.
2. **Never fabricate browser results.** None claimed; documented as a limitation.
3. **Never fabricate registry results.** None claimed; only the offline tarball
   gate is asserted.
4. **Never claim npm publishing succeeded unless it happened.** It did not run;
   not claimed.
5. **Protect all 529 v0.8 tests.** All retained; suite now 571.
6. **No deleting, skipping, or weakening tests.** No `.skip`/`.only`/`todo`
   introduced; verified by grep.
7. **No `any`.** None introduced in v0.9 source.
8. **No type suppressions.** No `@ts-ignore`/`@ts-expect-error` introduced.
9. **One graph only.** All inspection reads the single semantic graph.
10. **One reactive system only.** No second reactivity added.
11. **Separate inspection data from UI.** DevTools is headless data + a formatter.
12. **Runtime must not depend on DevTools.** Verified — no runtime import.
13. **Explicit DevTools activation, no prod cost.** Session exists only on
    `createDevTools`; not imported by runtime/CLI.

    no subscription/instrumentation.
15. **No sensitive values by default.** Resource/form/context/signal surfaces are

17. **No hosted or mandatory telemetry.** None; all boundaries are opt-in.
18. **DevTools must not expose secrets.** Sensitive-by-default enforced.
19. **DevTools disabled = normal production runtime.** Zero hot-path cost;
    nothing imports it in the runtime path.
20. **Improve `@streetui/testing` without a Jest/Vitest clone.** Helpers build on
    the real renderer; you bring the runner.
21. **First-class SSR→hydrate→assert testing.** `renderServerThenHydrate` added.
22. **Offline tarball gate remains valid.** Re-verified (17 packed, 16 consumed).
23. **Release automation is non-mutating.** `release-check.mjs` reads and reports
    only; emits an artifact manifest.
24. **Machine-readable release manifest.** `dist-tarballs/release-manifest.json`.
25. **Document only real APIs; additive changes preferred.** Docs describe shipped
    APIs (no `renderTestApp`); every API change is additive.
