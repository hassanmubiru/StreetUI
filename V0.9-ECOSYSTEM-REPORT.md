# StreetUI v0.9 — Ecosystem & Developer Experience

*Verified in the `/work` build copy. Nothing below is fabricated: browser and
registry remain unavailable and are reported as limitations, not simulated.*

## 1. Executive Summary

v0.9 makes an existing StreetUI application easier to build, debug, inspect,
test, understand, and release — without adding framework surface area. It is a
purely additive developer-experience layer: a first real (headless) DevTools
surface composed from the one semantic graph and the app's own reactive objects;
sharper testing helpers built on the real renderer; optional, privacy-safe
diagnostic and observability boundaries; a non-mutating release-readiness check
with a machine-readable manifest; and a documentation portal covering only real
APIs. No new renderer, reactive system, router, vdom, JSX, component library,
streaming SSR, or hosted telemetry was introduced. Every one of the 529 v0.8
tests is retained; the suite now stands at 571.

## 2. Baseline (starting state)

Starting from the completed and verified v0.8 milestone: 18 packages
(`core, state, graph, dsl, compiler, runtime, events, scheduler, dom, renderer,
router, forms, i18n, context, cli, devtools, testing`, plus private
`benchmarks`). v0.8 verified counts: build 27, typecheck 42, tests 529. Existing
inspection primitives `inspectApplication(compiled)` and
`diagnosePerformance(compiled)` were already present and became the foundation
for the DevTools surface rather than being replaced.

## 3. DevTools

`@streetui/devtools` now exposes `createDevTools(compiled, sources?, options?)`,
returning a headless `DevToolsSession { snapshot, refresh(), selectNode(id),
format() }`. It is a data-and-panels layer: any host (browser panel, CLI, test)
renders the snapshot. Nothing in the runtime or the CLI imports it, so a session
exists only when dev code opts in and production pays no cost. `refresh()` is the
only way values change (explicit-refresh protocol); `selectNode(id)` returns a
subtree from the captured graph to back a UI tree inspector. Panels:
application, graph, signals, performance (always), and router/resources/forms/
contexts/i18n (only when that live source is registered). Delivered with 11 new
panel tests.

## 4. Inspection Architecture

Inspection data is strictly separated from any UI. All inspectors are one-shot
reads (`peek`) of the single `CompiledApplication` graph plus the app's live
reactive objects — there is no second graph and no second reactive system, and
no inspector ever mutates or subscribes. The compiled graph knows signal *ids*,
not live instances, so the application registers whichever reactive surfaces it
wants visible via `DevToolsSources`. This keeps DevTools decoupled (structural
interfaces for router/forms/context/i18n, no extra dependencies) and keeps the
runtime unaware of DevTools entirely.

## 5. Signals

`inspectSignal(signal, options?)` reports `kind` (`writable` vs `derived`),
`value`, and `observerCount`, using the public `signalKind()`/`observerCount()`
API in `@streetui/state` — no private fields are read. Values can be redacted
via `{ redact: true }` or a mapping function, and the DevTools session can redact
all registered signals at once (`redactSignals`) for shared or recorded sessions.
The signals panel also lists `boundSignalIds` (distinct ids referenced anywhere
in the graph).

## 6. Router

`inspectRouter(router)` snapshots the current route's `path`, `pattern`,
`params`, `query`, and `isFallback` from the router's `currentRoute` signal. It
is inspection-only — navigation is never triggered from DevTools — and is
described by a structural `RouterLike` interface so devtools does not depend on
`@streetui/router`.

## 7. Resources

`inspectResource(resource, options?)` reports `status`, `loading`,
`isRefetching`, `hasData`, `hasError`, and the error's constructor name
(`errorName`). The loaded `data` and error `errorMessage` are omitted unless the
caller passes `{ includeData: true }`, because a resource payload commonly
carries user or secret data. This is the sensitive-by-default posture required by
§16/RULE 18.

## 8. Forms

`inspectForm(form, options?)` reports `fields`, per-field validation `errors`,
`touched`, `dirty`, `valid`, and `status`. Entered field `values` are omitted
unless the caller passes `{ includeValues: true }`, so passwords and other secret
inputs never reach a panel by default.

## 9. Hydration Diagnostics

`@streetui/renderer` gained dev-only, opt-in hydration diagnostics. Hydration
remains self-repairing and local: on a mismatch the renderer mounts a fresh
subtree in place and drops the offending element, and never throws globally. A
`HydrationDiagnosticSink` can *observe* those repairs, reporting mismatch `type`
(`tag-mismatch`/`missing-element`/`surplus-element`), `expected`, `found`,
`path`, `nodeId`/`nodeType`, recovery `action`, and a one-line `message`.
Helpers `createHydrationDiagnosticCollector()` and
`consoleHydrationDiagnosticSink()` are provided. With no sink attached there is
zero extra work on the hydration path.

## 10. Testing Improvements

`@streetui/testing` renders through the real renderer into a real
(happy-dom/jsdom) DOM. `render(app)` returns a `RenderResult` with container and
tag/text/selector queries; `renderOnce(app, fn)` auto-cleans up. Higher-level
helpers: `findByText`, `findByRole`/`findAllByRole` (explicit then implicit ARIA
role, optional accessible-name filter), `flushUpdates` (flush → microtask →
flush), and `waitFor` (poll with flushing until truthy). `renderServerThenHydrate`
provides a first-class SSR→HTML→hydrate→assert workflow with optional mismatch
collection. No private-graph access, no Jest/Vitest clone. Note: the spec's
candidate name `renderTestApp` was **not** added — the real, existing equivalents
are `render`/`renderServerThenHydrate`, and the docs reflect the real names.
