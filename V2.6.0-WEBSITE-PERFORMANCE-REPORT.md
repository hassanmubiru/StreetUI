# StreetUI 2.6.0 — Website Performance Report

**Phase 2 of the 2.6.0 "Production Website Validation" mission.**
Subject under test: the official StreetUI website, `examples/streetui-website/`, built
entirely in StreetUI and served through the single public `streetui` package.

Scope as specified: measure the real served website's **First Contentful Paint (FCP)**,
**Largest Contentful Paint (LCP)**, **Cumulative Layout Shift (CLS)**, and **Time To
Interactive (TTI)** in real browsers (Chrome 154, Firefox 155). This phase explicitly does
**not** compare StreetUI against other frameworks — it characterizes StreetUI's own
official application only.

---

## Status: BLOCKED (sandbox) — owned by the authoritative environment

These are browser-rendered metrics. FCP, LCP, CLS, and TTI are defined by the browser's
rendering pipeline and layout engine; they have no meaning outside a real browser. The
environment in which this phase was carried out has **no browser** (see
`V2.6.0-ENVIRONMENT-REPORT.md` §2: Chrome/Chromium/Firefox all absent, npm registry
blocked). Therefore **no paint or interaction timing was measured here, and none is
reported here.**

Consistent with the mission's evidence rule — *sandbox-absence is not fabrication, and
fabrication is not permitted* — this report does not contain invented FCP/LCP/CLS/TTI
numbers, and `benchmarks/results/v2.6/website-performance.json` carries
`status: "BLOCKED_SANDBOX"` with `measured: null` rather than placeholder values. A
sandbox probe must never write numbers into that file.

The authoritative environment (the user-confirmed machine with Chrome 154 and Firefox 155,
from which 2.2.0 and 2.3.0 were published) **owns** this measurement. The precedent is
already in-repo: `benchmarks/results/v2.5/visual-a11y.json` records a real
`chromium 154.0.8037.57` run, and `benchmarks/results/v2.5/streetui-firefox.json` a real
`firefox 155.0` run — both produced there, not here.

## What *was* established about the website (non-browser, in this environment)

These are real, in-process results and are the correct scope for a sandbox; they are the
server-side and structural foundations that a browser run would build on, not substitutes
for paint timings:

- The website renders on the server through the public `renderToString` / `renderHead`
  path for all 12 indexable routes plus the error routes, and the client mounts and
  navigates via `mountRouter` (website vitest 58/58).
- SSR output is **byte-identical** and stable: the SSR byte-identity gate passes on all
  five reference routes, exact string + byte-length + SHA-256, and each still matches the
  v1.6 golden baseline (overview 730 B `19d86cbb`, dashboard 925 B `4f6b4a39`, users
  3 610 699 B `f8f20c0d`, controls 36 551 B `3616bce9`, settings 926 B `42127b6f`). A
  smaller, deterministic server payload is the precondition for good FCP/LCP; this phase
  confirms that precondition without claiming the paint number itself.
- The client bundle carries **no SSR serializer leak** (leak-check CLEAN: minimal
  49 420 B, typical 78 798 B), so the bytes shipped to the browser are not inflated by
  server-only code — again a precondition for TTI, measured honestly as a bundle fact, not
  a browser timing.

## Hand-off checklist for the authoritative environment

To complete Phase 2, run in the authoritative environment and write the results into
`benchmarks/results/v2.6/website-performance.json` (replacing the BLOCKED stub):

1. Serve the built `examples/streetui-website/`.
2. In Chrome 154 and Firefox 155, collect FCP, LCP, CLS, TTI per indexable route (repeat
   runs, report medians; keep the two engines separate — do not average across engines).
3. Note the SSR byte sizes above as the server-payload context for LCP.
4. No cross-framework comparison in this phase.
