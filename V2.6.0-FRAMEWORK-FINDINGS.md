# StreetUI 2.6.0 — Framework Findings

Findings surfaced while validating the official StreetUI website
(`examples/streetui-website/`) as a real production application. Each finding is
classified and, where it implies a possible framework change, justified against the 2.6
rule set (no feature expansion, no size growth, no architecture change, no second
renderer/reactive system, single public `streetui` package preserved).

This file carries forward the six findings opened in 2.5 (F-1..F-6) with their 2.6
disposition, and adds one new finding (F-7) surfaced by the Phase 6 SEO/metadata work.

---

## Carry-forward disposition of 2.5 findings (F-1..F-6)

Phase 4 of 2.6 addressed the six 2.5 findings. Summary (full detail in
`V2.5.0-FRAMEWORK-FINDINGS.md` and the Phase 4 task record):

- **F-1 — missing first-class `code` / preformatted node.** Resolved at the application
  level without a new primitive; justified against the 6-point test and documented. No
  new leaf node shipped in the framework.
- **F-2..F-5 — documentation / types / router-outlet constant ergonomics.** Addressed
  (docs, type exports, exported `ROUTER_OUTLET_KEY` constant used by the website's
  server-side outlet fill). Additive only.
- **F-6 — `tsup` cannot bundle under the mounted sandbox workspace.** Confirmed to be a
  sandbox mount limitation, not a framework/app defect; not reproducible in the
  authoritative environment. Recorded honestly, not worked around with a fabricated
  "build passed" claim.

None of F-1..F-6 required a runtime primitive, a second renderer, or package
fragmentation.

## F-7 — `head()` managers are scoped per render context; two layers do not merge under `mountRouter` — **DOCUMENTATION / ERGONOMICS (not a defect)**

**How it surfaced.** Adding SEO metadata to the website (Phase 6) with the intuitive
two-layer design — a site-wide `head()` in the persistent shell plus a per-route
`head()` relying on `head()`'s last-in-document-order dedup to merge — produced
duplicate/dropped head tags on the client and on hydration (observed: two `<title>`s
after hydration; site-wide defaults pruned on fresh client mount).

**Root cause (confirmed at source).** In `packages/renderer/src/head.ts`,
`getHeadManager(ctx)` caches one `HeadManager` per `RenderContext`:

```
if (mutable.head === undefined) mutable.head = new HeadManager(ctx.dom, head);
```

`mountRouter` renders the persistent shell and each route in **separate runtimes**, so
shell and route each get their own `RenderContext` → their own `HeadManager`, both
writing to the single shared `document.head`. `HeadManager.apply()` adopts
server-planted tags, merges **only its own** contributions, then prunes every adopted
key **not** in its own set. The route manager therefore prunes the shell-only defaults
on the client, and the pre-planted server tags plus two managers duplicate tags on
hydration.

The renderer's own unit tests pass because they exercise `head()` within a **single**
render context. The website is the first consumer to declare `head()` in **both** the
shell and the routes under `mountRouter`, which is why this had not been seen before.

**This is NOT a sandbox/dist artifact.** It is a real per-`RenderContext` scoping
interaction, reproducible from source behavior.

**Resolution (application level, zero framework change).** Declare the **complete**
document head once per route via `pageHead()` + `pageLayout`; remove the shell's
`head()` call. `pageHead()` folds the site-wide defaults into every route, so one
`HeadManager` owns the whole `document.head`. Verified across SSR, client navigation,
and hydration with 26 passing tests (see `V2.6.0-SEO-METADATA-REPORT.md`).

**Framework-change decision (6-point).** No defect; website does not need it; a
cross-context merge would add new machinery (feature expansion, prohibited); a framework
change would risk the byte-identical SSR invariants; high risk for low reward. **Do not
change the framework in 2.6.** Follow-up: add a routing/metadata docs note stating that
under `mountRouter`, `head()` should be declared as one complete layer per route because
head managers are scoped per render context and do not merge across the shell/route
boundary. In-repo guidance is already present in `metadata.ts` and `shell.ts` headers.

**Classification: documentation / ergonomics.** The framework behaves correctly within
each render context; what was missing is guidance.

## What was NOT found in Phase 6

No new runtime primitive, no second renderer, no reactive-system change, and no package
split were needed to give the website correct, complete, per-route document metadata.
The public install surface (`npm install streetui`, entries `.`, `/server`, `/testing`)
is unchanged. Framework version remains **held at 2.5.0** pending the Phase 10 release
decision (`streetui.public.test.ts` asserts `VERSION === '2.5.0'`).
