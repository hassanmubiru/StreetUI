# StreetUI v1.0 — Stable Release Report

Prepared: 2026-09-24 · Channel: stable · Coordinated version: 1.0.0
Git commit (build tree): c386f182e05a2991771bf5dc8412ee06e71fd4d0
Runtime: Node v22.23.2

This is the required final report for the StreetUI 1.0 stabilization release. It
records, gate by gate, what was done and what evidence supports it. Two mandatory
gates — real-browser validation and registry publication — are reported **BLOCKED**
with no fabricated results, exactly as the environment requires. The report has 30
numbered sections followed by a compliance statement against all 33 release rules.

---

## 1. Executive summary

StreetUI 1.0.0 is a **stabilization** release, not a feature release. It freezes
the public API that grew across the 0.x series, aligns all 17 public packages on
one version (1.0.0), adds machine-checked API-contract and subsystem-stability
tests, strengthens the non-mutating release check, and documents the surface,
the semver promise, and the migration story. The full suite is green (619 tests,
up from the 571 baseline; none deleted, skipped, or weakened). Build 27/27 and
typecheck 27/27 pass. Packaging is proven to offline tarball install. The two
gates that require a real browser and a reachable registry cannot be executed in
this build sandbox and are reported BLOCKED with evidence of the blocker, not an
assumed pass.

## 2. Scope and non-goals

In scope: API stabilization, version alignment, compatibility verification,
release validation, documentation completeness, migration documentation, and
publishing-readiness up to the limits of the environment. Explicit non-goals:
no new framework features, no virtual DOM, no JSX, no React/Vue/Preact adapter,
no second renderer/reactive-system/graph, no streaming SSR. The 0.x → 1.0 change
is a promise about the existing surface, not an expansion of it.

## 3. Environment and constraints

Node v22.23.2. The monorepo is pnpm-workspaces + turbo. The build sandbox has no
package manager able to install, and no top-level `@streetui` symlinks: each
package resolves its declared dependencies through its own `node_modules`. New
packages or new dependency edges therefore cannot be added; all new tests live
inside an existing package and import that package's own public barrel plus only
already-declared siblings. Build/typecheck/test run via turbo in a working copy
with a PATH shim. Two hard environmental blockers, verified: no browser engine or
headless driver is present, and no npm registry is reachable. Offline tarball
install is feasible and is used as the strongest available packaging proof.

## 4. Package set and versions

Seventeen public packages, all publishing at **1.0.0**: core, state, graph, dsl,
compiler, runtime, events, scheduler, dom, renderer, router, forms, i18n,
context, devtools, testing, cli. `benchmarks` is private (not published). Seven
example apps are private and excluded from the public surface. Internal
dependency edges use `workspace:*` in-repo and are rewritten to the exact 1.0.0
at pack time, so no published package carries a `workspace:` protocol.

## 5. Version alignment (blocker resolved)

A genuine release blocker: `@streetui/cli` had `CLI_VERSION` pinned at `0.6.0`,
so `streetui --version` and the framework version stamped into scaffolded
projects were stale; and the `basic`/`ssr` project templates pinned their
`@streetui/*` dependencies at `0.1.0`, so `create` produced projects whose
dependencies did not match the framework. Fixed: `CLI_VERSION = '1.0.0'`;
templates now use the framework-version token replaced at scaffold time. A
contract test pins `CLI_VERSION` to `1.0.0` to prevent regression. The release
check treats any version divergence across the public set as an error and passes.

## 6. Public API inventory (§4/§44)

`scripts/api-inventory.mjs` parses each package's built `dist/index.d.ts`, splits
value from type exports, classifies stability, and verifies the `exports["."]`
types entry exists on disk. Result, written to `dist-tarballs/api-inventory.json`:
**168 public values and 171 public types across 17 packages**, every types entry
present. Per-package counts (values / types): core 23/15, state 12/12, graph
2/9, dsl 10/34, compiler 4/2, runtime 3/5, events 5/4, scheduler 5/3, dom 16/4,
renderer 28/8, router 10/14, forms 7/7, i18n 2/4, context 1/1, devtools 14/32,
testing 8/5, cli 18/12.

## 7. API freeze (§5)

The public API is exactly what each package re-exports from its public entry
point; anything not on that barrel is internal and unfrozen. From 1.0.0 the
frozen surface is governed by semver (section 9). The freeze is documented
authoritatively in `docs/api-v1.0.md`.

## 8. API stability tests (§6)

Every public package ships `src/public-api.stability.test.ts` asserting its
frozen list of value exports is present, and — where a signature is verified —
exercising the behavior from the public barrel only (no internal-path imports).
Examples: `state` signal get/set/derived/effect/batch; `renderer` SSR +
hydration node-adoption identity + tag-mismatch self-repair with an opt-in
diagnostic; `router` `matchPattern`/`matchRoutes`/`normalizePath`; `i18n`
`interpolate` + reactive `createI18n`; `forms` validators; `context`
provide/consume; `cli` frozen exports + `CLI_VERSION === '1.0.0'` + `parseArgs`.
A removed or renamed public export fails these tests.

## 9. Semver classification (§28)

Each export is classified stable / deprecated / experimental / internal
(internal = leading `_` or an `Internal` marker; deprecated/experimental only if
JSDoc-tagged at source). For 1.0.0 **all 339 exports are stable — zero
deprecated, experimental, or internal exports leak from any public barrel.**
Policy: breaking a stable export requires a major bump; additions are minors;
fixes are patches; raising the Node/browser baseline is a major.

## 10. Subsystem stability — SSR

`renderToString(compile(app))` renders real applications to deterministic HTML
(asserted content and structure, e.g. heading text inside `<h1`). SSR uses a
dedicated `ServerDOMAdapter` that builds strings and needs no DOM global, so it
runs in a plain Node process. Covered by `renderer` SSR tests and the offline
consumer smoke test (ESM + CJS entry points).

## 11. Subsystem stability — hydration (all mismatch types + local repair)

Hydration is validated end to end against a spec-compliant DOM: exact server-node
adoption (object identity preserved — the server node *is* the post-hydration
node, no recreation), single-listener event wiring, reactive updates on adopted
nodes, `when` toggling, keyed-list identity across reorders, controlled inputs,
unmount cleanup, and hydration-boundary preservation. Local self-repair is
verified for **all three** divergence types the hydrator distinguishes — a
`tag-mismatch` test, a `surplus-element` test, and a `missing-element` test added
in this release — each asserting the repair stays local and, opt-in, emits a
diagnostic with expected/found/path/action.

## 12. Subsystem stability — router

Pure matching and navigation are covered across the router's suites:
`normalizePath` idempotence and slash-normalization, `matchPattern('/users/:id',
'/users/5') → {id:'5'}` and non-match `null`, `matchRoutes → {route, params}`,
and target splitting. Router DOM behavior runs under the DOM environment.

## 13. Subsystem stability — resources

`resource()` has a comprehensive suite: idle/loading/success/error transitions,
refetch (previous data stays visible while status is loading), race-condition
resolution (last write wins), abort, explicit watch dependencies, cleanup
(status frozen at dispose), and the SSR hydration seed. This exercises the
reactive async lifecycle the DSL's `errorBoundary` and router integration rely on.

## 14. Subsystem stability — forms

Validators are verified from the public barrel: `required`, `minLength`,
`maxLength`, `email`, `pattern`, and `runValidators` first-failure semantics;
derived `dirty`/`valid`/submission-`status` signals are covered by the forms
suites.

## 15. Subsystem stability — i18n

`interpolate('Hi {name}', {name:'Ada'}) === 'Hi Ada'` and a missing token is
left literal (`'{missing}'`); `createI18n` resolves and translates, switches
locale reactively (a translation signal recomputes on locale change), and
reports key presence via `has`.

## 16. Subsystem stability — context

`createContext` with a default; `consume()` returns the default outside a
provider and `hasProvider()` is false; inside `provide(value, fn)` the consumed
value is the provided one and `hasProvider()` is true; the previous value is
restored on exit. No prop drilling, no global mutation.

## 17. Build verification

`turbo run build` — **27/27 packages successful**. No warnings-as-errors
regressions (the v0.6 CLI build trap remains fixed).

## 18. Typecheck verification

`turbo run typecheck` — **27/27 successful** under `strict` +
`exactOptionalPropertyTypes`. No `any`, no type-suppression directives were
introduced. (Combined build+typecheck: 54/54 turbo tasks.)

## 19. Test suite verification

`turbo run test` — **619 tests passed across 68 test files, 0 failures.** The
0.9 baseline was 571; the increase (+48) is entirely new API-contract and
subsystem-stability tests. No test was deleted, skipped, weakened, or rewritten
to hide a failure (RULES 6/7). Note: an isolated, non-reproducing `cli` e2e
failure observed once under full turbo parallelism did **not** recur on a forced
clean run and passes standalone; it was contention, not a regression, and was
resolved without touching any test.

## 20. Release check (§29)

`node scripts/release-check.mjs --release-version 1.0.0 --channel stable
--manifest` → **"RELEASE CHECK OK (0 warning(s))"** over 17 public packages. It
errors on: version divergence, missing per-package `README.md`/`LICENSE`,
`file:`/`link:`/`portal:` internal-source protocols, and missing `dist/` (unless
`--allow-missing-dist`). It does not mutate the tree.

## 21. Release manifest (§30)

The check writes `dist-tarballs/release-manifest.json`, enriched with the git
commit (c386f18…), channel (`stable`), package count (17), per-package versions,
and the findings/ok/error/warning summary.

## 22. Packaging — tarballs (§26)

`scripts/pack-tarballs.mjs` packs all **17 public packages to `*-1.0.0.tgz`**
under `dist-tarballs/`, rewriting `workspace:*` to the exact 1.0.0 so the
tarballs install without the workspace. The packed artifacts were verified, not
assumed.

## 23. Offline consumer verification (§27)

`scripts/consumer-smoke.mjs` installs the packed tarballs into a throwaway
project **with no workspace linking** and imports + server-renders through both
the ESM and CJS entry points. This proves a clean external consumer resolves and
runs the shipped artifacts. (`cli` is excluded from the framework consumer test
because it depends on the native `esbuild` binary fetched from a registry at
install time; its packaging metadata is still validated.)

## 24. Browser validation gate (§8/§9) — BLOCKED

**BLOCKED — no fabricated result.** No Chromium/Chrome, Firefox, or headless
driver (Playwright/Puppeteer) exists in the build sandbox. DOM behavior is
validated against **happy-dom**, a spec-compliant DOM implementation, in the
vitest `happy-dom` environment — not a shipped browser engine. No claim of
real-browser execution or a browser support matrix is made. Closing this gate
requires running the DOM suites in actual browsers via a browser-mode runner;
it is on the post-1.0 roadmap. Documented in `docs/browser-support.md`.

## 25. Registry / publishing gate (§10–§12) — BLOCKED

**BLOCKED — no fabricated result.** No npm registry is reachable from the build
environment. Nothing has been published; no "available on npm" or "install from
registry" claim is made. Packaging is proven up to locally-built tarballs and the
offline consumer install (sections 22–23). The publish step is intentionally
isolated as the one irreversible action and is documented in
`docs/release-process.md`.

## 26. Documentation completeness

Created for 1.0: `CHANGELOG.md` (0.1 → 1.0), `docs/api-v1.0.md` (public API
statement + report + semver policy + roadmap), `docs/migration-to-1.0.md`,
`docs/release-process.md`, `docs/browser-support.md`. The docs portal
(`docs/README.md`) and root `README.md` link them and carry the 1.0 status. A
stale "versions unchanged" note in `docs/publishing.md` was corrected. A claims
audit found no false "published"/"real-browser" assertions — only the honest
disclaimers. All docs describe real, shipped APIs.

## 27. Migration documentation

`docs/migration-to-1.0.md` states plainly that **there is nothing to migrate**:
no public API was removed, renamed, or changed in a breaking way from 0.9. It
records the two internal version-alignment fixes (CLI version, template pins),
the "update all `@streetui/*` together" rule, and what "stable" now commits the
project to.

## 28. Architectural integrity (RULES 12–18)

No virtual DOM, no JSX runtime, no React/Vue/Preact adapter, no second renderer,
no second reactive system, no second graph, no streaming SSR were introduced.
The pipeline remains DSL → compiler → one semantic application graph → runtime →
DOM renderer, with the framework's own reactivity (`.get()/.set()/.peek()/
.update()/.subscribe()`) and its own keyed reconciler. Stabilization touched
versions, tests, and docs — not architecture.

## 29. Known limitations and post-1.0 roadmap

Limitations: real-browser validation and registry publication are BLOCKED here
(sections 24–25). Roadmap (all additive / tooling unless a future major says
otherwise): real-browser CI validation; a registry publish pipeline from a
connected environment; optional streaming SSR; incremental additive growth of the
DSL, validators, and i18n formatters as the example apps prove need. Anything
needing a breaking change is deferred to a future major with a migration note.
