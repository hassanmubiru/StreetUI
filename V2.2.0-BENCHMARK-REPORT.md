## 2. Phase 3 — Benchmark-harness hardening

The goal of Phase 3 was **not** to produce new performance claims but to make the
harness produce a standardized, machine-readable, reproducible envelope and to
gate on its own correctness. Deliverables: `benchmarks/lib/bench-stats.mjs`
(statistics + environment capture + envelope schema `streetui-2.2-benchmark/v1`)
and the runnable `benchmarks/harness-hardening.mjs` (four checks).

**Gate result: PASS.** The four checks:

| Check | Result | What it proves |
|-------|--------|----------------|
| stats-correctness known-value lock | PASS | `summarize()` on the fixed dataset `[2,4,4,4,5,5,7,9]` returns mean 5, median 5, p95 9, variance 4, stddev 2, cv 0.4 — the statistics are exact and locked against regression |
| Node reproducibility (2 runs) | STABLE | run1 cv ≈ 0.479, run2 cv ≈ 0.443, median delta ≈ 0.09 % — both under the cv < 0.5 / medianDelta < 0.35 thresholds |
| envelope conformance | PASS | every emitted envelope validates against schema `streetui-2.2-benchmark/v1` |
| browser reproducibility | ✅ **PASS** | Chrome 154 present; StreetUI scenarios, list reorder, and React/Vue/Svelte competitors all measured |

**Explicit disclosure carried in the artifact:** the reproducibility workload is a
deterministic 200k-iteration pure-JS integer mix with no DOM and no IO. It is a
**Node/VM self-check only** — a proof that the harness and this VM produce stable
readings — and is *not* a framework or browser performance claim. Wall-clock
timings on a shared 2-core VM are inherently noisy and are labelled as such.

## 3. Phase 4 — Competitor harness

Phase 4 completes the cross-framework harness for five frameworks: **streetui,
React, Vue, Svelte, Solid**. The harness defines one shared methodology
(`benchmarks/methodology.md`) and a single result schema
(`streetui-2.2-competitors/v1`), and is orchestrated by
`benchmarks/run-competitors.mjs`.

**Shared scenario catalogue (A–H), identical workload for every framework:**

| ID | Scenario | Where it runs |
|----|----------|---------------|
| A | 10,000-row initial render | browser |
| B | one reactive update in a 10k tree | browser |
| C | keyed list ops on 10k items | browser |
| D | one signal → 1k/10k cells (fan-out) | browser |
| E | update one deep nested branch | browser |
| F | server render of the 10k app | Node |
| G | adopt server markup for the 10k tree (hydration) | browser |
| H | raw/gzip/brotli of runtime/minimal/full client bundles | Node |

**Svelte adapter repair (the Phase-4 code deliverable):** the pre-existing Svelte
adapter was broken in a way unique to Svelte's compiled model. Its scenario module
imported `render` from `svelte/server` and tried to server-render inside the
browser bundle — but Svelte 5 is *compiled*, so `svelte/server` `render()` only
works on server-compiled components; a client bundle cannot self-SSR the way
React's and Vue's runtime renderers can. That both broke the run and unfairly
pulled the server renderer into the client bundle (contaminating scenario H).
Additionally `svelte/src/ssr.mjs` never exported the `renderFlatHtml()` entry the
orchestrator needs. The repair added `renderFlatHtml()` to the Node SSR build,
removed the `svelte/server` import from the client scenario module, and rewrote
the hydration scenario to consume orchestrator-injected SSR markup and to skip
honestly when a browser is unavailable — matching the Solid adapter's contract.
`node --check` passes on both changed files. All four competitor adapters
(react, vue, svelte, solid) are `present: true` with SSR entries defined.

**Measurement result: PARTIALLY MEASURED.** React, Vue, and Svelte browser
scenarios were measured in Chrome 154. Solid produced no result file (adapter
requires investigation). Raw figures — no ranking:

| Framework | A: initial render | B: single update | SSR (Node) |
|---|---|---|---|
| React 19 | 8.2 ms | 1.5 ms | 2.97 ms |
| Vue 3 | 7.9 ms | 2.3 ms | 3.02 ms |
| Svelte 5 | 12.4 ms | 0.2 ms | 0.82 ms |
| Solid 1 | — (no result) | — | — |

The pre-existing `benchmarks/results/{react,vue,svelte,solid}.json` and
`comparison.json` (timestamp 2026-09-25) carry internally inconsistent metadata
(`domEnvironment='chromium (Playwright)'` yet `browserVersion=null`) and are
**not** used as 2.2 evidence — only the freshly measured figures above are.
