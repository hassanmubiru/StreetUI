### §2 — example-account flakiness resolved

The two `@streetui/example-account` "resources (plans)" tests that failed on the
host (Node v24.18.0) in v1.5 were caused by a fixed `tick(40)` (40 ms
wall-clock) racing a real localhost fetch — they passed on the VM's Node 22 but
not reliably on Node 24. In v1.6 both tests await the `onPlansResource` hook
(mirroring the existing `await form.submit()` pattern used by the forms tests)
instead of sleeping. **They are now deterministic across Node versions and pass
in both environments.** This is a test fix only; the runtime resource scheduler
is untouched.

## What changed, and why it is safe

### §4 / §5 — Measured the bottleneck first

Profiling `renderToString` for the 10k-row `/users` app (150,050 nodes:
80,029 elements + 70,021 text nodes) reproduced the phase split reported in v1.5:

| Phase | Share (pre-opt) | Median (pre-opt) |
|---|---|---|
| Mount (ServerDOM tree construction) | **61.3%** | 112.20 ms |
| Serialize (single-scan fast path) | **32.0%** | 58.50 ms |
| Escape (per-node, 0 special chars) | **~3.9%** | — |
| **Total** | | **183.04 ms** |

A ServerDOM census of the built tree identified the wasted allocation precisely:

| Store | Elements that use it | Empty allocations per render |
|---|---|---|
| `attributes` Map | 80,028 / 80,029 | — (keep eager) |
| `properties` Map | 1 / 80,029 | **80,028 wasted** |
| `style` (ServerStyle + inner Map) | 0 / 80,029 | **80,029 wasted** |

Every `ServerElement` eagerly allocated a `properties` Map and a `ServerStyle`
(which holds its own Map), even though ~0 % of elements in the 10k-row app use
them. That is ~240,000 wasted allocations per `/users` render, all in the
dominant mount phase.

### §6 / §8 — The optimization: lazy allocation (reuse the model, don't replace it)

`properties` and `style` became **lazily allocated**:

- Backing fields `_properties` / `_style` default to `null`.
- The public `properties` / `style` **getters** allocate on first write only.
- `serializeAttributes` reads the raw `_properties` / `_style` backing fields
  directly, so **a read never forces allocation**.
- A `null` store is serialized identically to an empty store (both produce
  nothing) — output is byte-identical by construction.

This is a change to *when* the existing objects are created, not a separate SSR
semantics engine and not a compiler change. The public API of `ServerElement` is
unchanged: `.properties` and `.style` still return `Map` / `ServerStyle`
respectively (via getters), and the new `_properties` / `_style` fields are
internal.

### §7 — Compiler changes: none

The gain is a runtime allocation change. A per-compile static-subtree analysis
was scoped (§6 / §7) and deferred: it would add per-compile diagnostic overhead
and risk the byte-identity / hydration invariants for a phase that is no longer
dominated by removable allocation. No new per-compile diagnostic was added.

legacy 104.03 ms vs shipped 62.84 ms = **1.66× faster**, byte-identical.
(v1.5 reported 1.63×; the small difference is run-to-run variance; both confirm

|---|---|---|

routes. An unset store serialized to nothing before; a `null` store is skipped
the same way.

### Remaining bottlenecks

After lazy allocation, mount is still the largest phase (~56%). The remaining
mount cost is graph traversal + instance creation + `ServerElement` /
`ServerText` construction + `attributes` Map population + `children.push` —
work intrinsic to building 150,050 nodes, not wasted allocation. Serialize
(~35%) is already the v1.4 single-scan fast path. Further gains would require a
compile-time static-subtree serialization plan (scoped under §6/§7 and
deferred).

## Methodology

Node/happy-dom timings use `perf_hooks`; each scale-sensitive scenario runs in
its own child process. DOM mutations are counted at the single
`BrowserDOMAdapter` choke point. Timed scenarios report median/p95/min/max/sample
count. The SSR profiler runs ≥15 iterations per configuration; the same-process
A/B holds the JIT-warmed tree constant across legacy and shipped serializer paths
so the comparison is fair. **No number in this report crosses environments** —
no happy-dom value is presented as, or compared against, a browser value.
