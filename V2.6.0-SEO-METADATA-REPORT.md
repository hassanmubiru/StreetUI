# StreetUI 2.6.0 — SEO / Document-Metadata Validation Report

**Phase 6 of the 2.6.0 "Production Website Validation" mission.**
Subject under test: the official StreetUI website, `examples/streetui-website/`, built
entirely in StreetUI and served through the single public `streetui` package
(entry points `.`, `/server`, `/testing`).

Scope: validate that the website emits correct, per-route document metadata on the
server, that the client applies and updates that metadata on navigation, and that a
server render is adopted on hydration without duplicating head tags. This phase also
discharges a mandated **correction** of an inaccurate claim in the 2.5 findings.

Environment: Node v24.18.0, Chrome 154 available, npm registry reachable. All structural
assertions below are made through the framework's own public API and the `happy-dom`
test environment. Browser crawlers, social-card scrapers, and search-engine indexers are
out-of-process consumers outside the scope of this file (see "Engine boundary").

---

## 1. Headline correction (mandated)

The 2.5 website **declared no `head()` calls at all.** No route emitted a `<title>`,
description, canonical URL, Open Graph, Twitter card, or robots directive. The
`V2.5.0-FRAMEWORK-FINDINGS.md` document listed "head metadata" among the capabilities
the website exercised; that was inaccurate. Document metadata was a genuine **coverage
gap**, not an exercised capability.

That correction has been applied to `V2.5.0-FRAMEWORK-FINDINGS.md` (a dated
"Correction (2.6)" note now sits in the "What was explicitly NOT found" section and
points here). 2.6 closes the gap by adding a real metadata layer to the website and, in
doing so, surfaced a legitimate framework dogfooding finding (F-7, below).

---

## 2. What the website now emits

Metadata is declared with StreetUI's own first-class `head()` primitive (shipped in
2.0) — the same semantic-graph + handler model as the rest of the framework, not a
bolt-on. The source of truth is `examples/streetui-website/src/metadata.ts`.

Every indexable route emits a complete document head:

- `<title>` — the page's own title suffixed with the site name (`"About · StreetUI"`).
- `<meta name="description">` — the page's description, or the site default when a page
  supplies none.
- `<link rel="canonical">` — `SITE.baseUrl + path`.
- `<meta name="robots">` — `index,follow` by default; `noindex` on the 404 page and on
  unknown docs/blog routes.
- `<meta name="theme-color">`, `<link rel="icon">`, `<meta name="viewport">`,
  `<meta charset>` — site-wide document defaults.
- Open Graph: `og:site_name`, `og:type` (`website`), `og:title`, `og:description`,
  `og:url`, `og:image`.
- Twitter: `twitter:card` (`summary_large_image`), `twitter:title`,
  `twitter:description`, `twitter:image`.

`SITE` constants: name `StreetUI`, baseUrl `https://streetui.dev`, default title
`StreetUI — a semantic-graph UI framework`, theme-color `#0b0d10`, OG image
`https://streetui.dev/og-card.png`.

---

## 3. The single-head-layer design and WHY (finding F-7)

The non-obvious part of adding metadata to a **router-driven** app was *where* to declare
it. The intuitive design is two layers: a site-wide `head()` in the persistent shell
(charset, viewport, favicon, OG site fields) plus a per-route `head()` layering the
page title / description / canonical on top, relying on `head()`'s documented
last-in-document-order dedup to merge them. That is exactly what was tried first, and
it does **not** compose on the client.

**Root cause (confirmed at framework source, not inferred).**
In `packages/renderer/src/head.ts`, `getHeadManager(ctx)` caches one `HeadManager` on
the per-render `RenderContext`:

```
if (mutable.head === undefined) mutable.head = new HeadManager(ctx.dom, head);
```

`mountRouter` renders the persistent shell and **each route** in **separate runtimes**
(`createRuntime({ renderer })` for the shell, then a fresh one per route), hence
separate `RenderContext`s → **separate `HeadManager`s**, both writing to the one shared
`document.head`. A `HeadManager.apply()` adopts any server-planted tags
(`_adoptServerTags` scans for `[data-streetui-head-key]`), merges only **its own**
contributions, then prunes every key in `_applied` that is **not** in its own merged
set. So the route's manager, which never saw the shell's site-wide defaults, prunes
them on the client — and on hydration the pre-planted server tags plus the two managers
yield **duplicate** tags (e.g. two `<title>`s).

This is a real per-`RenderContext` scoping interaction, **not** a sandbox/dist artifact.
The renderer's own unit tests pass because they declare `head()` within a **single**
render context; the website is the first consumer to declare `head()` in **both** the
shell and the routes under `mountRouter`.

**Fix adopted — website level, zero framework change.**
Declare the **complete** document head in **one** layer: the route layer, via
`pageHead()` + `pageLayout`. `pageHead()` folds the site-wide defaults
(`siteDefaults()`) into every route's head, so one `HeadManager` owns the whole
`document.head`. The shell's `head()` call was removed (an explanatory comment in
`shell.ts` records why). `siteHead()` is retained as a standalone complete default head
for non-router / full-page renders and is unit-tested in isolation.

This complies with the 2.6 rules: no new primitive, no second renderer/reactive system,
no architecture change, no package fragmentation. It is an **application-level** design
decision driven by how the existing `head()` + `mountRouter` behave.

**F-7 classification: documentation / ergonomics finding, not a defect.** The framework
behaves correctly within each render context. What is missing is guidance: `head()`
under `mountRouter` should be declared as one complete layer per route, because head
managers are scoped per render context and do not merge across the shell/route boundary.
This is now documented in-repo (`metadata.ts` and `shell.ts` headers) and is a candidate
for the framework's routing/metadata docs. No code change to the framework is proposed
for 2.6 on the strength of this finding alone (see §7).

## 4. Server-side verification (SSR)

`renderWebsite(path).head` (which calls the public `renderHead(compiled)`) was asserted
across all 12 indexable routes plus the error routes:

- A single `<title>` carrying the page's **own** title — the route head fully overrides
  the default, which never leaks (`head` does not contain `SITE.defaultTitle`).
- `name="description"`, `rel="canonical"` with the exact `baseUrl + path` href,
  `name="robots"` = `index,follow`, `property="og:title"`, `property="og:url"`,
  `name="twitter:card"` = `summary_large_image`.
- Exactly **one** `<title>` and **one** canonical per route (dedup collapse verified by
  counting matches, not just presence).
- 404 and unknown docs/blog routes emit `content="noindex"` and never `index,follow`;
  the home route emits `index,follow` and never `noindex`.
- Site-wide defaults inherited on a route page (`/about`): `theme-color`, `rel="icon"`,
  `og:site_name` = `StreetUI`.
- Every emitted tag carries the `data-streetui-head` adoption marker and
  `data-streetui-head-key="title"` (a server-render invariant).

## 5. Client-side verification (apply + navigate)

Mounting the real website (`mountWebsite`) into `happy-dom` and asserting on the live
`document.head`:

- On mount at `/about`, `document.head` has exactly **one** `<title>` reading
  `About · StreetUI` and exactly **one** `link[rel="canonical"]` →
  `https://streetui.dev/about`. No stacking of a shell default plus a route title.
- Client navigation (`/about` → `/api` → `/playground`) updates the title and canonical
  in place with **no duplicate** tags at any step.

Client-side assertions are made by tag + semantics (the `<title>` text, the canonical
href, and element counts) rather than by the `data-streetui-head` marker. The marker is
a server-render hydration-adoption hint; asserting on it client-side would couple the
app tests to a renderer implementation detail, and `happy-dom`'s `innerHTML`
serialization was observed to omit the marker on client-DOM-created tags even though the
runtime stamps it. The site invariant that matters — "exactly one correct title /
canonical, updated on navigation" — is what is checked.

---

## 6. Hydration verification

A server render (`renderWebsite('/about')`) is planted into the shared document
(body + head string, markers present), then the website is mounted with `hydrate: true`.
After hydration: still exactly **one** `<title>` and **one** canonical total — the
server tags are **adopted**, not duplicated — and the title still reads
`About · StreetUI`. The pre-hydration assertion keeps the marker-based count
(`title[data-streetui-head]` = 1) on the planted server string, which is a legitimate
server-output invariant.

## 7. Framework-change question (6-point justification)

Should 2.6 change the framework so two `head()` layers merge across the shell/route
boundary under `mountRouter`?

1. **Is there a real defect?** No — each `HeadManager` is correct within its render
   context. The behavior is an emergent property of per-context scoping + router's
   separate runtimes, not a bug in `head()`.
2. **Does the website need it?** No. The single-layer design produces complete, correct,
   non-duplicated metadata on server, client, and hydration (§4–§6, 26 passing tests).
3. **Would a fix add surface/size?** Yes — cross-context head merging would mean a
   shared/document-scoped head manager or a merge pass across runtimes, i.e. new
   machinery, exactly the feature-expansion 2.6 prohibits.
4. **Is it reversible/contained?** The application-level fix is fully contained in the
   website; a framework change would touch the renderer's head subsystem and risk the
   byte-identical SSR invariants.
5. **Risk vs reward?** High risk (SSR/hydration regressions) for low reward (an
   ergonomic convenience already solved at the app level).
6. **Decision.** Do **not** change the framework for this in 2.6. Document the
   one-complete-layer-per-route guidance (done, in-repo) and leave a routing/metadata
   docs note as the follow-up. Recorded in `V2.6.0-FRAMEWORK-FINDINGS.md` as F-7.

## 8. Test evidence

`examples/streetui-website` vitest, Node v22.23.2:

- `src/website-seo.test.ts` — 18 tests (SSR per-route metadata, dedup, noindex,
  default inheritance; client apply + navigation; hydration adoption). **PASS.**
- `src/_dbg.test.ts` — 8 tests (pure-function unit coverage of `siteHead()` /
  `pageHead()`: title suffix, canonical construction, description fallback, OG/Twitter
  mirroring, default `robots: index,follow` + `noindex` override). **PASS.**
- Full website suite (`website.test.ts`, `website-regression.test.ts`,
  `website-seo.test.ts`, `_dbg.test.ts`): **58/58 PASS.**
- Full monorepo gate: `turbo run typecheck` **48/48**, `turbo run test` **48/48**
  (website task executed on cache-miss and passed).

Environment note: `_dbg.test.ts` is a vestigial debug filename that could not be renamed
or deleted in the sandbox (mounted-workspace deletion restriction). Its contents are the
metadata pure-function unit suite; recommend renaming to `metadata.test.ts` in the
authoritative environment.

## Engine boundary

Crawler rendering, social-card scraping, and real search-engine indexing are
out-of-process consumers verified in the authoritative environment. This report proves
the markup the framework **emits** and how the client applies/updates/adopts it — not
third-party consumption. No browser-measured SEO signal is claimed here.
