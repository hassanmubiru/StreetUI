## 4. Real-browser validation — PASS

`node scripts/browser-harness.mjs` → **OK** — Chromium 153.0.8010.12, results
written to `benchmarks/results/v1.3/streetui-browser.json`.

All measurements are from a real Chromium engine running the full
`examples/streetui-performance-app`, instrumented via `window.__bench` with
`performance.now`, `PerformanceObserver` (longtask), `MutationObserver`, and
`requestAnimationFrame`.

| Scenario | Result | Notes |
|----------|--------|-------|
| Initial mount /users (10k rows) | **197.1 ms** | 80,031 DOM nodes; real browser paint path |
| Reactive search narrow (10k→0) | **127.8 ms**, 10,004 mutations | `query.set('aa')` |
| Reactive search clear (0→10k) | **167.8 ms**, 10,004 mutations | `query.set('')` |
| Reverse sort (worst-case reorder) | **56.6 ms**, 20,002 mutations | full list inversion |
| Router navigation (4 routes) | 29.5 / **399.9** / 52.4 / 31.4 ms | /dashboard, /users, /settings, / — /users is slow (10k row mount) |
| Hydration /users (10k rows) | **162.6 ms** | nodesBefore=80,029; nodesAfter=80,029; **0 nodes added** — pure adoption |
| Frame pacing (big-list reorder, 500 ms) | 2 frames, maxFrame 510.9 ms | 2/2 frames over 16.67 ms budget — not 60 fps capable on this workload |
| Memory (6 mount/interact/unmount cycles) | 239 MB stable | no heap growth across cycles; indicative (no explicit GC API in browser) |
| Long tasks | **9 tasks, 2,913 ms total** | dominated by 10k-row mount and list reorders |

**Notable real-browser findings:**

- The zero-node hydration guarantee holds in a real browser: 80,029 nodes before
  and after hydration, 0 added.
- Initial mount in Chromium (197 ms) is ~10× faster than happy-dom (2,072 ms),
  confirming that happy-dom is a poor proxy for absolute timing.
- Frame pacing is not 60 fps on the 10k-row reorder workload — this is the
  primary client-side weakness (consistent with §15).
- 9 long tasks (>50 ms) were recorded; the largest are the 10k-row initial mount
  and the full-list sort reorder.

## 5. Competitor comparison — PASS

`node benchmarks/run-competitors.mjs` → **done (4/4 frameworks measured)**,
results written to `benchmarks/results/comparison.json`.

Competitors installed as pinned devDependencies in `benchmarks/competitors/*/`
(never in StreetUI's runtime). React and Vue ran full browser scenarios via
Playwright; Svelte ran SSR only (browser build issue in this harness); Solid ran
Node scenarios only (no SSR entry in the harness). **No ranking is asserted** —
the environments differ (StreetUI uses happy-dom for Node scenarios; React/Vue/
Solid use Chromium for browser scenarios), so cross-framework absolute numbers
are not directly comparable. Relative patterns are noted where they are clear.

| Framework | Version | Initial render | Single update | List reorder | SSR (ms) | Bundle gzip |
|-----------|---------|---------------|--------------|-------------|----------|-------------|
| **StreetUI** | 1.3.0 | 104.2 ms (happy-dom) | **0.03 ms** | 325.5 ms (happy-dom) | 30.9 ms | 20,105 B |
| React | 19.1.0 | 14 ms (Chromium) | 2.4 ms | 127.8 ms | 3.2 ms | 58,225 B |
| Vue | 3.5.13 | 8.2 ms (Chromium) | 2.3 ms | 8.1 ms | 3.2 ms | 23,540 B |
| Svelte | 5.19.0 | — | — | — | **0.88 ms** | **3,962 B** |
| Solid | 1.9.3 | 11.4 ms (Chromium) | **0 ms** | **0.9 ms** | — | **2,441 B** |

**What the data says (no ranking):**

- StreetUI's **single reactive update (0.03 ms)** is in the same range as Solid
  (0 ms rounded) and faster than React/Vue (~2.3 ms). Fine-grained reactivity is
  a strength.
- StreetUI's **list reorder (325 ms, happy-dom)** trails all compiler-optimised
  frameworks measured in a browser. This is expected: the LIS-based reconciler
  pays per-node comparison cost that compile-time optimised frameworks eliminate.
  The happy-dom vs Chromium environment gap makes the absolute comparison
  unfair — StreetUI's real-browser list reorder was not measured in this run.
- StreetUI's **SSR (30.9 ms)** trails React (3.2 ms), Vue (3.2 ms), and Svelte
  (0.88 ms). StreetUI SSR walks the full compiled SAG graph and serialises state;
  the gap is real and is the primary SSR bottleneck.
- StreetUI's **bundle (20,105 B gzip)** is larger than Svelte (3,962 B) and
  Solid (2,441 B) but smaller than React (58,225 B). It includes a full runtime,
  router, forms, i18n, context, devtools, and CLI — a different scope than
  Svelte/Solid's minimal runtimes.

## 8. Developer ergonomics findings (§18)

The real application was built entirely on the existing frozen API. No new public
API was needed.

- **The builder DSL carried the whole app.** Components are plain functions
  `(page, deps) => void` using `page.section`, `page.heading/text/button/link/
  input`, `page.listOf`, `page.when`, `page.form`, `page.errorBoundary`.
- **No free-standing element factories.** `div()`, `button()`, `text()` are not
  exported. This is intentional — documented in [`docs/components.md`](docs/components.md).
- **Reactivity needed no additions.** `signal`/`derived`/`effect`/`batch` plus
  `get()` vs `peek()` covered every case including the derived 10k-row projection.
- **Forms and resources are just signals.** Both compose with `when` /
  `errorBoundary` without a special rendering path.

## 13. Known limitations

- **happy-dom timings are indicative, not authoritative.** StreetUI's Node
  scenario timings are ~10× slower than Chromium (confirmed by comparing
  happy-dom vs real-browser initial mount: 2,072 ms vs 197 ms). Cross-framework
  comparisons that mix happy-dom and Chromium numbers are not valid — this report
  notes the environment for each row.
- **Competitor browser scenarios are partial.** Svelte had a Playwright build
  issue (SSR-only result). Solid has no SSR entry in the harness (Node-only
  result). A complete apples-to-apples comparison requires all frameworks running
  identical browser scenarios.
- **No StreetUI browser list-reorder number.** The real-browser harness measures
  the full performance app workloads but does not yet run an isolated list-reorder
  scenario comparable to the competitor `listUpdate_reorder_ms` column.
- **Frame pacing is not 60 fps on 10k-row workloads.** This is the primary
  client-side weakness and is expected to persist until the list reconciler is
  optimised (v1.4 target).

## 14. Measured strengths

- **Hydration is zero-node** in a real Chromium browser: 80,029 nodes before and
  after, 0 added — adoption guarantee holds at scale.
- **Fine-grained reactivity** (0.03 ms single update) is competitive with Solid.
- **Form field isolation** is DOM-verified: typing one field does not mutate
  unrelated fields.
- **No node-count drift** across repeated full app lifecycle cycles.
- **Bundle is smaller than React** (20,105 B gzip vs 58,225 B) with a far broader
  included feature set.
- **0 bytes of framework CSS.**

---

## 15. Measured weaknesses

- **Initial mount of 10k rows** is the dominant cost: 197 ms in Chromium, 9 long
  tasks recorded. Large first-paint tables are where StreetUI spends its time.
- **List reorder** trails Solid (0.9 ms) and Vue (8.1 ms) significantly. The LIS
  reconciler pays per-node cost that compile-time frameworks eliminate.
- **SSR throughput** (30.9 ms) trails React (3.2 ms), Vue (3.2 ms), Svelte
  (0.88 ms) significantly. Full SAG traversal + state serialisation is expensive.
- **Bundle is larger than Svelte/Solid** (3,962 B / 2,441 B gzip). StreetUI
  includes router, forms, i18n, context, devtools, CLI in the single package;
  Svelte/Solid's numbers reflect minimal runtimes.
- **Frame pacing** at 60 Hz is not achieved on the 10k-row reorder workload
  (maxFrameMs = 510.9 ms).

## 16. Ranking

**None.** The environments are not equivalent (StreetUI Node/happy-dom vs
competitors in Chromium for most scenarios). Where the environments are
comparable (SSR, single reactive update), the numbers are stated plainly in §5
without a ranking. A definitive ranking requires all five frameworks measured
under identical conditions in the same Chromium instance — that harness extension
is the v1.4 target.
