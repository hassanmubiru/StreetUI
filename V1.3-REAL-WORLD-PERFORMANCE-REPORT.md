## 8. Developer ergonomics findings (§18)

The real application was built entirely on the existing frozen API. No new public
API was needed.

- **The builder DSL carried the whole app.** Components are plain functions
  `(page, deps) => void` using `page.section`, `page.heading/text/button/link/
  input`, `page.listOf`, `page.when`, `page.form`, `page.errorBoundary`.
- **No free-standing element factories.** `div()`, `button()`, `text()` are not
  exported. This is intentional — documented in [`docs/components.md`](docs/components.md).
- **Reactivity needed no additions.** `signal`/`derived`/`effect`/`batch` plus
  `get()` vs `peek()` covered every case including the derived 10k-row projection.
- **Forms and resources are just signals.** Both compose with `when` /
  `errorBoundary` without a special rendering path.

## 13. Known limitations

- **happy-dom timings are indicative, not authoritative.** StreetUI's Node
  scenario timings are not browser paint/layout numbers. A real-browser
  comparison is required for absolute client-side timing, and it is BLOCKED here
  (no Chromium/Playwright).
- **No real-browser numbers at all.** Real-browser mount/reorder/frame-pacing/
  hydration/JS-heap metrics are BLOCKED — the environment has no browser. These
  are the primary v1.4 targets and require a Chromium-capable environment.
- **No competitor numbers at all.** React/Vue/Svelte/Solid cannot be installed
  (registry 403) or run (no browser). A complete apples-to-apples comparison
  requires all frameworks running identical browser scenarios on the same
  machine — deferred until the environment allows it.
- **Frame pacing on 10k-row workloads is unmeasured here** and remains a stated
  concern to be quantified once a browser is available (v1.4 target).

## 14. Measured strengths

- **Hydration is zero-node** (Node/happy-dom): 0 nodes created adopting the
  10k-row view — the adoption guarantee holds at scale.
- **Fine-grained reactivity** is independent of N: toggling 1 of 1,000 controls
  costs the same 2 structural writes as 1 of 100.
- **Form field isolation** is DOM-verified: typing one field does not mutate
  unrelated fields.
- **No node-count drift** across repeated full app lifecycle cycles; 0 orphans.
- **Bundle is smaller than React** (20,105 B gzip vs the widely-cited ~58 KB React
  baseline) with a far broader included feature set — measured for StreetUI only.
- **0 bytes of framework CSS.**

---

## 15. Measured weaknesses

- **Initial mount of 10k rows** is the dominant cost in Node/happy-dom
  (2,072 ms, 150,032 nodes). Large first-paint tables are where StreetUI spends
  its time; a real-browser figure is needed to size the true cost.
- **List reorder** is a per-node LIS cost (9,803 structural writes for a sort
  reorder of 10k). Whether this is a client-side bottleneck must be confirmed in
  a browser (BLOCKED here).
- **SSR throughput** walks the full SAG graph and serialises state; the
  per-route body sizes are large by design for the 10k-row route. SSR timing
  optimisation is a v1.4 target.
- **Bundle is larger than minimal runtimes** would be, because StreetUI includes
  router, forms, i18n, context, devtools, and CLI in one package.
