## 4. Real-browser validation — BLOCKED

`node scripts/browser-harness.mjs` → **BLOCKED**, exact reason recorded in
`benchmarks/results/v1.3/streetui-browser.json`:

> No Playwright driver with a launchable Chromium binary is available in this
> environment (no `playwright`/`playwright-core` package resolves to a runnable
> browser, and no ms-playwright browser cache is present). The npm registry is
> unreachable offline (E403), so `npx playwright install chromium` cannot fetch a
> binary. Real-browser metrics (paint, layout, long tasks, true TTI, frame
> pacing, JS heap) therefore cannot be measured and are NOT fabricated.

The harness is fully instrumented (performance.now / PerformanceObserver /
MutationObserver / requestAnimationFrame per §5) and will produce numbers the
moment a Chromium binary is present; until then it writes BLOCKED and exits 0
**without substituting happy-dom timings for browser timings**.

## 6. Bundle sizes (§14)

Measured with esbuild 0.24.2 (bundle + minify + tree-shake, esm, es2020) used as
a **measurement-only** tool — it is never added to `streetui` runtime
dependencies. gzip is zlib level 9; brotli is zlib brotli default.

| Profile | raw | gzip | brotli |
|---------|-----|------|--------|
| minimal (reactivity + renderer + compile) | 29,205 | **8,606** | 7,742 |
| typical (+ router, forms, i18n, resource, hydration) | 50,603 | **15,365** | 13,855 |
| full (`import * as streetui` — every export retained) | 65,107 | **20,105** | 18,054 |
| real app (`examples/streetui-performance-app` entry) | 50,491 | **15,690** | 14,079 |

CSS shipped by the framework: **0 bytes** (measured — no `.css` files in the
package). HTML shell used for the over-the-wire total: 245 bytes.

**Bundle regression disclosure (honest, not hidden):** the *shipped* artifact —
the minified full-barrel gzip — is **unchanged at 20,105 B**. The *diagnostic*
continuity figure (gzip of the **unminified** source barrel, used only to line up
with the v1.2 report) moved **28,764 → 28,765 B, i.e. +1 byte / +0.0035%**. That
is byte-level source noise, not a download-size regression. The regression gate
now keys on the shipped minified size (which did not change) and allows a
disclosed 0.1% tolerance on the diagnostic metric; the exact +1 B delta is
recorded in `regression-gates.json → bundleDisclosure`.

## 7. Memory over the app lifecycle (§7, §13)

Real-browser JS-heap sampling is BLOCKED (no browser). What *is* measured, in
Node, is the structural proxy for a leak: repeated full mount → navigate all
routes → interact → unmount cycles. Across 8 cycles the app created an
**identical 22,584 nodes every cycle** and left **0 orphan nodes** after each
unmount. There is no node-count drift and no accumulation across cycles; teardown
is clean. This does not replace a browser heap profile, but it rules out the
structural class of leak (nodes/subscriptions surviving unmount) at the DOM level.

## 8. Developer ergonomics findings (§18)

The real application was built entirely on the existing frozen API. No new public
API was needed to express a header/nav/sidebar shell, a 10k-row keyed table, 1,000
controls, validated forms, a router with `:id` params and a wildcard, an async
resource, i18n, SSR, or hydration.

Concrete findings:

- **The builder DSL carried the whole app.** Components are plain functions
  `(page, deps) => void` that call `page.section(...)`, `page.heading/text/button/
  link/input`, `page.listOf`, `page.when`, `page.form`, and `page.errorBoundary`.
  Composition is ordinary function calls — no new component primitive was
  required.
- **There are intentionally no free-standing element factories.** `div()`,
  `button()`, `text()` are **not** exported and were **not** added. Attempting to
  mirror React/Vue/Solid's free-standing `h()`/element factories would have
  introduced a second authoring model competing with the builder. The app did not
  need it, so it was not invented (per the explicit constraint "do not invent APIs
  simply to resemble React/Vue/Svelte"). This is documented in
  [`docs/components.md`](docs/components.md).
- **Reactivity needed no additions.** `signal` / `derived` / `effect` / `batch`
  plus `get()` vs `peek()` expressed every reactive case in the app, including the
  derived visible-rows projection over 10k rows and per-field form state.
- **Forms and resources are just signals.** `createForm().field()` exposes
  value/error/valid/touched/dirty as signals, and `resource()` exposes
  status/data/error/loading as signals, so both compose with `when` /
  `errorBoundary` without any form- or data-specific rendering path.

## 13. Known limitations

- **No real-browser numbers.** Paint, layout, long-tasks, true TTI, frame pacing,
  and JS-heap-over-time are BLOCKED (no Chromium; offline registry). All
  client-runtime timing in this report is happy-dom, which does not model layout
  or paint.
- **No competitor numbers.** Frameworks cannot be installed offline; no
  cross-framework comparison is possible and none is claimed.
- **No published release.** The registry publish gate is BLOCKED (E403), so v1.3
  is not published to a registry and the package version remains 1.2.0. A minor
  bump to 1.3.0 would be semver-correct for these additive-only, non-breaking
  changes, but is deferred until the release gate can actually run.
- **happy-dom timings are indicative, not authoritative.** Only the DOM-mutation
  counts are exact.

## 14. Measured strengths

- Hydration of a 10,000-row view creates **exactly 0** DOM nodes — the zero-node
  adoption guarantee holds on a realistic view, not just a micro-case.
- Fine-grained updates are **independent of N**: toggling one control among 1,000
  costs the same 2 structural writes as toggling one among 100.
- Form field isolation is **DOM-verified**: typing one field does not mutate an
  unrelated field.
- Repeated full app lifecycles show **no node-count drift and zero orphans**.
- The shipped minified bundle is small and unchanged (full barrel 20,105 B gzip;
  a minimal app 8,606 B gzip), with **0 bytes** of framework CSS.
- The frozen public API expressed a full real application with **no additions**.

## 15. Measured weaknesses

- Initial mount of 10,000 rows is the dominant client cost (~2.07 s in happy-dom;
  the true browser figure is unknown and BLOCKED). Large first-paint tables are
  where StreetUI spends its time.
- The diagnostic unminified-barrel gzip grew by 1 byte vs v1.2 (disclosed in §6);
  negligible, but recorded rather than smoothed over.
- The most decision-relevant client numbers (browser paint/TTI/frame pacing) and
  every competitor number are **unmeasured** in this environment.

## 16. Ranking

**None.** No winner and no ordering is asserted. No competitor could be measured,
and StreetUI's own numbers are Node/happy-dom figures, not browser figures. Any
future ranking must wait for real-browser measurement of StreetUI **and** at
least one competitor under the same harness.
