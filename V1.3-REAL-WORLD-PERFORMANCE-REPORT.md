## 5. Competitor comparison

Source: `node benchmarks/run-competitors.mjs` → `benchmarks/results/comparison.json`
timestamp: 2026-09-25T07:47:38Z. Competitors installed as pinned devDependencies
in `benchmarks/competitors/*/` — never in StreetUI's runtime.

**Important environment note:** StreetUI's Node scenarios run in happy-dom;
React, Vue, and Solid browser scenarios run in Chromium via Playwright. These are
different environments. The table states the environment for each row. Direct
absolute comparison between happy-dom and Chromium timings is not valid.

| Framework | Version | Environment | Initial render | Single update | List reorder | SSR | Bundle gzip |
|-----------|---------|-------------|---------------|--------------|-------------|-----|-------------|
| **StreetUI** | 1.3.0 | happy-dom (Node) | 104.2 ms | **0.03 ms** | 325.5 ms | 30.9 ms | 20,105 B |
| React | 19.1.0 | Chromium | 9.9 ms | 2.1 ms | 158.4 ms | 3.0 ms | 58,225 B |
| Vue | 3.5.13 | Chromium | 9.5 ms | 2.9 ms | **10.5 ms** | 4.3 ms | 23,540 B |
| Svelte | 5.19.0 | Chromium (SSR only) | — | — | — | **1.0 ms** | **3,962 B** |
| Solid | 1.9.3 | Chromium | 11.7 ms | **0 ms** | **1.1 ms** | — | **2,441 B** |

**What the data shows (no ranking):**

- StreetUI single update (0.03 ms, happy-dom) is in the same order of magnitude
  as Solid (0 ms rounded, Chromium). Fine-grained reactivity is a strength, but
  the environments differ.
- StreetUI SSR (30.9 ms) is substantially slower than React (3.0 ms), Vue
  (4.3 ms), and Svelte (1.0 ms) — all measured in the same Node environment for
  SSR. This is a real gap.
- StreetUI list reorder (325.5 ms, happy-dom) cannot be fairly compared to
  Vue/Solid/React (Chromium) — a same-environment comparison is needed.
- StreetUI bundle (20,105 B gzip) includes router, forms, i18n, context,
  devtools, CLI. Svelte (3,962 B) and Solid (2,441 B) are minimal runtimes with
  different scope.
- Svelte browser scenarios did not complete (build issue in the harness).
- Solid has no SSR entry in the current harness configuration.

## 9. Known limitations

- **Same-environment competitor comparison is incomplete.** StreetUI's Node
  scenarios run in happy-dom; competitors run in Chromium. A complete apples-to-
  apples comparison requires all five frameworks in the same Chromium instance.
  That is the v1.4 harness target.
- **Svelte browser scenarios did not complete** (Playwright build issue in the
  harness). SSR-only result recorded.
- **Solid has no SSR scenario** in the current harness.
- **No StreetUI browser list-reorder number** from an isolated scenario comparable
  to the competitor `listUpdate_reorder_ms` column.
- **Live-HTTP-API example tests** (example-account: 2, example-data: 5) fail
  because no API server is running — pre-existing, not regressions.

## 10. Measured strengths

- Zero-node hydration confirmed in real Chromium at 10k scale.
- Fine-grained reactivity (0.03 ms single update, happy-dom) is competitive.
- No node-count drift across 8 full lifecycle cycles.
- 0 bytes of framework CSS shipped.
- Bundle smaller than React (20,105 B vs 58,225 B) with broader scope.
- Full real application expressed with zero API additions.

---

## 11. Measured weaknesses

- **SSR is slow** (30.9 ms vs React 3.0 ms, Vue 4.3 ms, Svelte 1.0 ms) — all
  measured Node/happy-dom, so the comparison is valid. Full SAG traversal + state
  serialisation is the bottleneck.
- **Initial mount of 10k rows** produces 14 long tasks in real Chromium
  (4,084 ms total). Frame pacing not 60 fps on this workload.
- **List reorder** (325.5 ms, happy-dom) is expected to trail compiler-optimised
  frameworks — same-environment measurement deferred to v1.4.
