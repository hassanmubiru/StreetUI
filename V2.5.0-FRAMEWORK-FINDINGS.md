# StreetUI 2.5.0 — Framework Findings

Findings surfaced by building the official website entirely in StreetUI
(`examples/streetui-website/`). Each is classified, backed by concrete evidence from the
app, and paired with a proposed direction. **No API was auto-added to make a finding go
away.** Where a change is warranted it is proposed with its justification; where the
current behavior is correct-but-sharp it is recorded as documentation/ergonomics.

Classification vocabulary: BUG · API DESIGN · MISSING PRIMITIVE · DX PROBLEM ·
PERFORMANCE · ACCESSIBILITY · TOOLING · DOCUMENTATION · APPLICATION ARCHITECTURE.

---

## F-1 — No first-class code / preformatted node — **MISSING PRIMITIVE**

**Evidence.** A documentation site must render source listings, yet the DSL has no
`code`/`pre` node. `components.ts :: codeExample` composes a `container` + a label `text`
+ the source passed through `text()`. Because `text()` escapes at the renderer boundary
(correctly, for safety), the sample renders as a single escaped string; monospace,
whitespace preservation, and wrapping are entirely CSS applied to the `#…-code-src` id.
There is no node that signals "this is preformatted code" semantically or to assistive
technology, and no seam for syntax highlighting without reaching outside the graph.

**Impact.** Every docs page, the API reference, and the blog depend on this workaround.
It works and stays safe (no raw-HTML injection), but the framework cannot express a
`<pre><code>` structure or expose a `code`/`language` affordance.

**Proposed direction (not yet implemented).** Add a `code(source, { language?, id? })`
leaf (and/or a `pre` container) that renders `<pre><code>` with escaped text and an
optional `data-language`. This is additive, needs no new reactive machinery, and would
let the website drop its CSS-only workaround. Deferred pending a scope decision — flagged,
justified, **not** silently shipped.

## F-2 — `derived` is `ReadonlySignal`, easy to over-annotate as `Signal` — **DX PROBLEM / DOCUMENTATION**

**Evidence.** Three fields were initially typed `Signal<…>` but assigned the result of
`derived(...)`: `theme.ts :: resolved` and `label`, `shell.ts :: SearchState.results`, and
`components.ts :: countLabel`'s return. `tsc --noEmit` rejected all of them (a
`DerivedSignal` has no `set`/`update`/`_flushBatch`/`_flush`). Fix was to annotate them
`ReadonlySignal<…>`.

**Assessment.** The type system behaved **correctly** — a derived value must not be
writable. This is not a bug. The finding is ergonomic: the natural first instinct when
holding "a signal of X" is to write `Signal<X>`, and the compiler error (missing internal
members like `_flushBatch`) does not immediately point the author at "use
`ReadonlySignal`." 

**Proposed direction.** Documentation: make the `signal` vs `derived` → `Signal` vs
`ReadonlySignal` distinction explicit in the reactivity docs with the exact "annotate
derived results as `ReadonlySignal`" guidance. Optionally, keep internal signal members
non-enumerable in the public types so the mismatch error reads in terms of `set`/`update`
rather than private fields. No runtime change.

## F-3 — Optional DSL option fields reject explicit `undefined` under exactOptional — **API DESIGN**

**Evidence.** The root tsconfig enables `exactOptionalPropertyTypes`. `pageLayout`'s
`opts.lead?: string` could not receive `doc?.summary` / `post?.date` (both
`string | undefined`) — the callers in `routes.ts` passed a value that *might* be
`undefined`, which `exactOptional` forbids against a `lead?: string` field. Fix was to
widen the public parameter to `lead?: string | undefined`.

**Assessment.** This is a real public-surface ergonomics issue, not just an app bug: any
consumer under `exactOptionalPropertyTypes` who forwards a possibly-`undefined` value into
an optional DSL option hits the same wall. The framework's own option types should model
"omitted *or* explicitly undefined" where that's the intended contract.

**Proposed direction.** Audit public option interfaces and, for fields where passing
`undefined` is semantically equal to omission, declare them `field?: T | undefined`. This
is type-only and backward compatible. Recorded as a cross-cutting API-design item rather
than fixed only at the app layer.

## F-4 — Router-outlet id/key is a dual source of truth for hydration — **API DESIGN / DOCUMENTATION**

**Evidence.** `routerOutlet(scope, id)` emits `container('router-outlet', …, { id })` with
a default id of `streetui-router-outlet`. The site needed (a) a stable, human-meaningful
outlet id for the skip link target (`#page-outlet`) and (b) SSR to fill that same outlet
inline so hydration adopts the server node. Getting adoption right required emitting the
server outlet with the **same key *and* the same id** that `routerOutlet` uses, and
passing `outletId: 'page-outlet'` to `mountRouter` as well. Three places must agree
(the explicit `routerOutlet` id, `mountRouter.outletId`, and the SSR `renderOutlet`
container's key+id) or hydration silently recreates the subtree.

**Assessment.** Hydration adoption keyed on node identity is the right mechanism, but the
contract ("key and id must match across SSR/runtime/outlet") is implicit and easy to get
subtly wrong — the failure mode is a silent re-render, not an error.

**Proposed direction.** Documentation: a short "custom outlet id + SSR adoption" recipe
spelling out the three-way agreement. Optionally expose the outlet key as a constant
alongside `ROUTER_OUTLET_ID` so SSR code references one symbol instead of restating the
literal. No runtime change required.

## F-5 — `RouteContext.query` is a `URLSearchParams`, not a record — **DOCUMENTATION**

**Evidence.** The `/examples` route initially read `ctx.query.q` as if `query` were a
plain object; it is a `URLSearchParams`, so the correct read is
`ctx.query.get('q')` (returns `string | null`, guarded with `q !== null`).

**Assessment.** The API is reasonable and standards-aligned; the trap is purely
expectational. Recorded so the routing docs and the `RouteContext` typedoc show a
`query.get(...)` example rather than leaving the shape to be inferred.

## F-6 — `tsup` cannot bundle under the mounted workspace — **TOOLING (sandbox-only)**

**Evidence.** `node_modules/.bin/tsup` fails with
`EPERM: operation not permitted, unlink '…/tsup.config.bundled_*.mjs'`: tsup writes a temp
config next to the project and deletes it, but the mounted directory forbids `unlink`.
Bundling the three entries directly with the repo's esbuild (ESM, `platform: neutral`,
`streetui*` externalized) succeeds, and the bundled `server-entry.js` runs and renders
real SSR HTML.

**Assessment.** This is an environment limitation of the sandbox mount, **not** a framework
or app defect, and not reproducible in the authoritative environment where `tsup` runs
normally. Recorded here (rather than silently worked around) to keep the build story
honest. No fabricated "build passed via tsup" claim is made.

## What was explicitly NOT found

Building the full site exercised components, signals/derived/effects, routing with
dynamic + query params, nested persistent shell/outlet, resources-style derived data,
forms and bound inputs, conditional `when`, keyed `listOf`, SSR + hydration, head
metadata, and the testing utilities — none of which required a new runtime primitive, a
second renderer, or any package fragmentation. The public install surface
(`npm install streetui`) is unchanged. The findings above are ergonomics, documentation,
one genuinely missing leaf node (F-1), and one sandbox tooling limitation (F-6).

## Execution boundary

Performance and accessibility findings that require a real browser or screen reader are
**not** included here; they are owned by `V2.5.0-PERFORMANCE-REPORT.md` and
`V2.5.0-ACCESSIBILITY-REPORT.md` and must be produced in the authoritative environment.
No perf/AT finding is asserted from sandbox probes.
