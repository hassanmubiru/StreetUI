# StreetUI v0.7 — Performance, Compiler Optimization & Production Hardening

**Final Report.** Version milestone: **v0.7** (following the established v0.4/
v0.5/v0.6 convention in this repo — release milestones are tracked by report,
package.json stays at the workspace-internal `0.1.0`; no breaking changes were
made, so this is safe and consistent with prior releases). All numbers below are
measured; none is estimated. See `docs/performance.md`,
`docs/performance-v0.7.md`, and `docs/performance-hotpaths.md` for detail.

---

## 1. Executive Summary

v0.7 followed the mandate literally: **measure first, then optimize, then
measure again, then verify.** A runnable benchmark suite (`@streetui/benchmarks`,
`node:perf_hooks`, no heavy dependency) was built covering the compiler, mount,
reactivity, conditionals, keyed lists, attributes, events, unmount, SSR, and
hydration across 10/100/1000/5000 sizes. A v0.6 baseline of 84 results was
captured, then two CPU profiles were taken.

The profiling showed that under the `happy-dom` test environment, **native DOM
construction and GC dominate absolute time**, and the framework's own JS is a
modest slice. The keyed-list reconciler — the usual suspect — measured at ~1.8%
self-time and was confirmed **appropriate and left unchanged** (§11). Exactly
**one** optimization met the evidence-and-improvement bar: hoisting the per-node
`Set` allocation in `applyNodeProps` to module scope (**OPT-1**), which produced
a **stable ~11–19% improvement on SSR** and neutral results elsewhere, with no
regression at scale and no semantic change. A second candidate (**OPT-2**,
in-place `setProp`) was measured, found to be ~1% and to conflict with
serialization identity, and was **deferred rather than applied on a guess**.

Bundle size, a count-only devtools performance surface (§20), and dev-only
performance diagnostics (§21) were added. The protected test baseline (**496**)
is fully intact; total tests are now **512**. Build **26/26**, typecheck
**41/41**.

## 3. Benchmark Infrastructure

New package **`@streetui/benchmarks`** (private, not published):

- `node:perf_hooks` `performance.now()`; warmup + measurement iterations; per
  benchmark median / p95 / min / max / mean / ops-per-sec; captured environment
  header (Node / OS / CPU / arch / cores / memory).
- Suites: compiler, render, reactivity, conditional, keyed-lists, attributes,
  events, unmount, ssr, hydration.
- `run.js` installs `happy-dom` **before** any renderer import, runs all or a
  `--suite=` subset, writes `results/{baseline,current}.json`, and prints a
  current-vs-baseline comparison with per-benchmark % delta and an
  improved/regressed/unchanged/new status.
- **No hard pass/fail thresholds** and **kept separate from correctness tests**
  (benchmarks never run under `npm test`).
- 7 harness correctness tests (`summarize` math, `bench` setup/run/teardown
  counts, `environment`, `compareResults` statuses) — all passing.

## 5. Optimizations Implemented

### OPT-1 — Hoist `applyNodeProps` skip-key `Set` (APPLIED, KEPT)

- **Problem:** `applyNodeProps` (`packages/renderer/src/mount.ts`) allocated
  `new Set([...15 keys])` on **every element node** — N allocations per mount
  and per SSR pass — purely to test key membership, feeding GC.
- **Evidence:** 3.5% self-time in the mount CPU profile, 2.4% in the list
  profile; the set is invariant across nodes.
- **Change:** moved it to a module-level `const SKIP_PROP_KEYS: ReadonlySet<string>`.
  Membership test identical.
- **Result:** controlled repeated runs show a **stable -11% to -19% on
  `ssr/render-to-string`** (n=1000 and n=5000); SSR n=1000 improved in both
  isolated (-14 to -16%) and full-suite (-11.4%) modes. Mount n=5000 improved
  mildly; keyed lists neutral (±~2.4%, within noise).
- **Tradeoff:** none. Set is shared and read-only; 4 new memory/cleanup cycle
  tests guard against cross-mount contamination. 111 renderer tests pass.

### OPT-2 — In-place `GraphNode.setProp` (MEASURED, DEFERRED)

- **Problem/Evidence:** `this.props = {...this.props,[key]:value}` clones on every
  write; ~1% self-time in the list profile only, absent from the mount profile.
- **Change considered:** `this.props[key] = value`.
- **Result/why deferred:** `Graph.serialize()` shares the live `props` reference
  into its snapshot, so in-place mutation would alter serialization identity
  semantics. Not worth a semantic risk for ~1%. **Reverted/never applied** per
  §23. Documented as a measured, minor, deferred item.

Post-OPT-1 full run written to `results/current.json`. The **trustworthy**

| ssr/render-to-string | 1000 | 1.22 | 1.02–1.08 | **-11% to -16%** |
| render/mount | 5000 | 57.71 | ~54–58 | mild / noise |

Small-n (≤100) deltas of ±10–90% in the raw comparison are **noise on a 2-vCPU

## 7. Compiler

Measured `dsl-build` and `compile` at 10/100/1000/5000. No hot path surfaced in
profiling; **no optimization applied** (valid §27 result — "measured, no
significant bottleneck"). Compiler timings are dominated by graph construction
that is already linear and allocation-light.

## 8. Graph

`GraphNode.setProp` was the only graph-level candidate (OPT-2) — measured ~1%,
deferred for the serialization-identity reason above. `GraphNode` child
management and `serialize()` were reviewed and left unchanged. No second graph
representation was introduced anywhere (§22).

## 9. Reactivity

`update-subscribers` (1/10/100/1000), `derived-chain`, and `batch-writes` were
benchmarked. The targeted patch path (signal → `NodeInstance` → single prop) is
already minimal (n=1000 = 0.175 ms). `batch()` semantics (depth counter,
last-write-wins, single flush) were **preserved** — no change. No optimization
applied; documented as already-appropriate.

## 10. Renderer

OPT-1 lives here. Beyond it, `applyProp`/`patchProp` already hoist their
`DOM_PROPERTIES`/`BOOLEAN_ATTRS` sets and short-circuit on `Object.is`; the
renderer already skips unnecessary DOM writes on unchanged props. No further
renderer change was justified by evidence.
